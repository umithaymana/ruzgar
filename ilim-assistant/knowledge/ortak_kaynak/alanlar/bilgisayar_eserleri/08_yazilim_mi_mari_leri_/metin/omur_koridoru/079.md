Interoperability Models There are two distinct protocols relevant to interoperability: an &quot;application protocol&quot; and a &quot;transport protocol&quot;. The transport protocol defines how the iCalendar objects are sent between the sender and receiver. This document focuses on the application protocol. Application Protocol In the iTIP model, an iCalendar object is created and managed by an &quot;Organizer&quot;. The &quot;Organizer&quot; interacts with other CUs by sending one or more of the iTIP messages listed above. &quot;Attendees&quot; use the &quot;REPLY&quot; method to communicate their status. &quot;Attendees&quot; do not make direct changes to the master iCalendar object. They can, however, use the &quot;COUNTER&quot; method to suggest changes to the &quot;Organizer&quot;. In any case, the &quot;Organizer&quot; has complete control over the master iCalendar object. 2.1.1 . Scheduling State There are two distinct states relevant to iCalendar objects used in scheduling: the overall state of the iCalendar object and the state associated with an &quot;Attendee&quot; in that iCalendar object. The state of an iCalendar object is defined by the &quot;STATUS&quot; property and is controlled by the &quot;Organizer.&quot; There is no default value for the &quot;STATUS&quot; property. The &quot;Organizer&quot; sets the &quot;STATUS&quot; property to the appropriate value for each iCalendar object. The state of a particular &quot;Attendee&quot; relative to an iCalendar object used for scheduling is defined by the &quot;PARTSTAT&quot; parameter in the &quot;ATTENDEE&quot; property for each &quot;Attendee&quot;. When an &quot;Organizer&quot; issues the initial iCalendar object, &quot;Attendee&quot; status is typically unknown. The &quot;Organizer&quot; specifies this by setting the &quot;PARTSTAT&quot; parameter to &quot;NEEDS-ACTION&quot;. Each &quot;Attendee&quot; modifies their &quot;ATTENDEE&quot; property &quot;PARTSTAT&quot; parameter to an appropriate value as part of a &quot;REPLY&quot; message sent back to the &quot;Organizer&quot;. 2.1.2 . Delegation Delegation is defined as the process by which an &quot;Attendee&quot; grants another CU (or several CUs) the right to attend on their behalf. The &quot;Organizer&quot; is made aware of this change because the delegating &quot;Attendee&quot; informs the &quot;Organizer&quot;. These steps are detailed in the &quot;REQUEST&quot; method sections for the appropriate components. Daboo Standards Track [Page 10] RFC 5546 iTIP December 2009 2.1.3 . Acting on Behalf of Other Calendar Users In many organizations, one user will act on behalf of another to organize and/or respond to meeting requests. iTIP provides two mechanisms that support these activities. First, the &quot;Organizer&quot; is treated as a special entity, separate from &quot;Attendees&quot;. All responses from &quot;Attendees&quot; flow to the &quot;Organizer&quot;, making it easy to separate a &quot;Calendar User&quot; organizing a meeting from &quot;Calendar Users&quot; attending the meeting. Additionally, iCalendar provides descriptive roles for each &quot;Attendee&quot;. For instance, a role of &quot;chair&quot; may be ascribed to one or more &quot;Attendees&quot;. The &quot;chair&quot; and the &quot;Organizer&quot; may or may not be the same &quot;Calendar User&quot;. This maps well to scenarios where an assistant may manage meeting logistics for another individual who chairs a meeting. Second, a &quot;SENT-BY&quot; parameter may be specified in either the &quot;Organizer&quot; or &quot;Attendee&quot; properties. When specified, the &quot;SENT-BY&quot; parameter indicates that the responding CU acted on behalf of the specified &quot;Attendee&quot; or &quot;Organizer&quot;. 2.1.4 . Component Revisions The &quot;SEQUENCE&quot; property is used by the &quot;Organizer&quot; to indicate revisions to the calendar component. When the &quot;Organizer&quot; makes changes to one of the following properties, the sequence number MUST be incremented: o &quot;DTSTART&quot; o &quot;DTEND&quot; o &quot;DURATION&quot; o &quot;DUE&quot; o &quot;RRULE&quot; o &quot;RDATE&quot; o &quot;EXDATE&quot; o &quot;STATUS&quot; In addition, changes made by the &quot;Organizer&quot; to other properties MAY also require the sequence number to be incremented. The &quot;Organizer&quot; CUA MUST increment the sequence number whenever it makes changes to properties in the calendar component that the &quot;Organizer&quot; deems will Daboo Standards Track [Page 11] RFC 5546 iTIP December 2009 jeopardize the validity of the participation status of the &quot;Attendees&quot;. For example, changing the location of a meeting from one location to another distant location could effectively impact the participation status of the &quot;Attendees&quot;. Depending on the &quot;METHOD&quot;, the &quot;SEQUENCE&quot; property MUST follow these rules in the context of iTIP: o For the &quot;PUBLISH&quot; and &quot;REQUEST&quot; methods, the &quot;SEQUENCE&quot; property value is incremented according to the rules stated above. o The &quot;SEQUENCE&quot; property value MUST be incremented each time the &quot;Organizer&quot; uses the &quot;ADD&quot; or &quot;CANCEL&quot; methods. o The &quot;SEQUENCE&quot; property value MUST NOT be incremented when using &quot;REPLY&quot;, &quot;REFRESH&quot;, &quot;COUNTER&quot;, &quot;DECLINECOUNTER&quot;, or when sending a delegation &quot;REQUEST&quot;. In some circumstances, the &quot;Organizer&quot; may not have received responses to the final revision sent out. In this situation, the &quot;Organizer&quot; may wish to send an update &quot;REQUEST&quot; and set &quot;RSVP=TRUE&quot; for all &quot;Attendees&quot; so that current responses can be collected. The value of the &quot;SEQUENCE&quot; property contained in a response from an &quot;Attendee&quot; may not always match the &quot;Organizer&#x27;s&quot; revision. Implementations may choose to have the CUA indicate to the CU that the response is to an iCalendar object that has been revised, and allow the CU to decide whether or not to accept the response. Whilst a change in sequence number is indicative of a significant change to a previously scheduled item, &quot;Attendee&quot; CUAs SHOULD NOT rely solely on a change in sequence number as a means of detecting a significant change. Instead, CUAs SHOULD compare the old and new versions of the calendar components, determine the exact nature of the changes, and make decisions -- possibly based on &quot;Calendar User&quot; preferences -- as to whether the user needs to be explicitly informed of the change. 2.1.5 . Message Sequencing CUAs that handle the iTIP application protocol must often correlate a component in a calendar store with a component received in the iTIP message. For example, an event may be updated with a later revision of the same event. To accomplish this, a CUA must correlate the version of the event already in its calendar store with the version sent in the iTIP message. In addition to this correlation, there are several factors that can cause iTIP messages to arrive in an unexpected order. That is, an &quot;Organizer&quot; could receive a reply to Daboo Standards Track [Page 12] RFC 5546 iTIP December 2009 an earlier revision of a component after receiving a reply to a later revision.

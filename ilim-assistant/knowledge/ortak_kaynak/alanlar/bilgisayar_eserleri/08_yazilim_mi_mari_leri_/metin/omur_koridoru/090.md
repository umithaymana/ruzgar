Working With Recurrence Instances iCalendar includes a recurrence grammar to represent recurring events. The benefit of such a grammar is the ability to represent a number of events in a single object. However, while this simplifies creation of a recurring event, meeting instances still need to be referenced. For instance, an &quot;Attendee&quot; may decline the third instance of a recurring Friday event. Similarly, the &quot;Organizer&quot; may change the time or location to a single instance of the recurring event. Since implementations may elect to store recurring events as either a single event object or a collection of discrete, related event objects, the protocol is designed so that each recurring instance may be both referenced and versioned. Hence, implementations that choose to maintain per-instance properties (such as &quot;ATTENDEE&quot; property &quot;PARTSTAT&quot; parameter) may do so. However, the protocol does not require per-instance recognition unless the instance itself must be renegotiated. The scenarios for recurrence instance referencing are listed below. For purposes of simplification, a change to an event refers to a &quot;trigger property.&quot; That is, a property that has a substantive effect on the meeting itself, such as start time, location, due date (for &quot;VTODO&quot; calendar components), and possibly description. &quot;Organizer&quot;-initiated actions: o deletes or changes a single instance of a recurring event o makes changes that affect all future instances o makes changes that affect all previous instances o deletes or modifies a previously changed instance Daboo Standards Track [Page 77] RFC 5546 iTIP December 2009 &quot;Attendee&quot;-initiated actions: o changes status for a particular recurrence instance o sends a &quot;COUNTER&quot; for a particular recurrence instance An instance of a recurring event is assigned a unique identification, &quot;RECURRENCE-ID&quot; property, when that instance is renegotiated. Negotiation may be necessary when a substantive change to the event or to-do has been made (such as changing the start time, end time, due date, or location). The &quot;Organizer&quot; can identify a specific recurrence instance using the &quot;RECURRENCE-ID&quot; property. The property value is equal to the date/time of the instance. If the &quot;Organizer&quot; wishes to change the &quot;DTSTART&quot;, the original, unmodified &quot;DTSTART&quot; value of the instance is used as the value &quot;RECURRENCE-ID&quot; property, and the new &quot;DTSTART&quot; and &quot;DTEND&quot; values reflect the change. 3.7.2 . Attendee Property Considerations The &quot;ORGANIZER&quot; property is required on published events, to-dos, and journal entries for two reasons. First, only the &quot;Organizer&quot; is allowed to update and redistribute an event or to-do component. It follows that the &quot;ORGANIZER&quot; property MUST be present in the event, to-do, or journal entry component so that the CUA has a basis for authorizing an update. Second, it is prudent to provide a point of contact for anyone who receives a published component, in case of problems. Email addresses that correspond to groups of &quot;Calendar Users&quot; could be specified as a mailto: URI [ RFC2368 ] calendar user address. Sending email to such an address results in email being sent to multiple recipients. Such an address may be used as the value of an &quot;ATTENDEE&quot; property. Thus, it is possible that the recipient of a &quot;REQUEST&quot; does not appear explicitly in the list. It is recommended that the general approach to finding a &quot;Calendar User&quot; in an &quot;Attendee&quot; list be as follows: 1. Search for the &quot;Calendar User&quot; in the &quot;Attendee&quot; list where &quot;CUTYPE=INDIVIDUAL&quot; 2.

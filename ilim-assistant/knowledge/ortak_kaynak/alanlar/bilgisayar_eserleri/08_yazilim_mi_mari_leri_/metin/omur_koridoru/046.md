Example: Well-Known URI Redirects to Actual &quot;Context Path&quot; A CalDAV server has a &quot;context path&quot; that is &quot;/servlet/caldav&quot;. The client will use &quot;/.well-known/caldav&quot; as the path for its &quot;bootstrapping&quot; process after it has first found the FQDN and port number via an SRV lookup or via manual entry of information by the user, from which the client can parse suitable information. When the client makes an HTTP request against &quot;/.well-known/caldav&quot;, the server would issue an HTTP redirect response with a Location response header using the path &quot;/servlet/caldav&quot;. The client would then &quot;follow&quot; this redirect to the new resource and continue making HTTP requests there to complete its &quot;bootstrapping&quot; process. 6 . Client &quot;Bootstrapping&quot; Procedures This section describes a procedure that CalDAV or CardDAV clients SHOULD use to do their initial configuration based on minimal user input. The goal is to determine an http: or https: URI that describes the full path to the user&#x27;s principal-URL [ RFC3744 ]. 1. Processing user input: * For a CalDAV server: + Minimal input from a user would consist of a calendar user address and a password. A calendar user address is defined by iCalendar [ RFC5545 ] to be a URI [ RFC3986 ]. Provided a user identifier and a domain name can be extracted from the URI, this simple &quot;bootstrapping&quot; configuration can be done. + If the calendar user address is a &quot;mailto:&quot; [ RFC6068 ] URI, the &quot;mailbox&quot; portion of the URI is examined, and the &quot;local-part&quot; and &quot;domain&quot; portions are extracted. + If the calendar user address is an &quot;http:&quot; [ RFC2616 ] or &quot;https:&quot; [ RFC2818 ] URI, the &quot;userinfo&quot; and &quot;host&quot; portion of the URI [ RFC3986 ] is extracted. The &quot;mailbox&quot; portion of the email address is examined, and the &quot;local-part&quot; and &quot;domain&quot; portions are extracted. 2. Determination of service FQDN and port number: * An SRV lookup for _caldavs._tcp (for CalDAV) or _carddavs._tcp (for CardDAV) is done with the extracted &quot;domain&quot; as the service domain. * If no result is found, the client can try _caldav._tcp (for CalDAV) or _carddav._tcp (for CardDAV) provided non-TLS connections are appropriate. * If an SRV record is returned, the client extracts the target FQDN and port number. If multiple SRV records are returned, the client MUST use the Priority and Weight fields in the record to determine which one to pick (as per [ RFC2782 ]). * If an SRV record is not found, the client will need to prompt the user to enter the FQDN and port number information directly or use some other heuristic, for example, using the extracted &quot;domain&quot; as the FQDN and default HTTPS or HTTP port numbers. In this situation, clients MUST first attempt an HTTP connection with TLS. 3. Determination of initial &quot;context path&quot;: * When an SRV lookup is done and a valid SRV record returned, the client MUST also query for a corresponding TXT record and check for the presence of a &quot;path&quot; key in its response. If present, the value of the &quot;path&quot; key is used for the initial &quot;context path&quot;. * When an initial &quot;context path&quot; has not been determined from a TXT record, the initial &quot;context path&quot; is taken to be &quot;/.well-known/caldav&quot; (for CalDAV) or &quot;/.well-known/carddav&quot; (for CardDAV). * If the initial &quot;context path&quot; derived from a TXT record generates HTTP errors when targeted by requests, the client SHOULD repeat its &quot;bootstrapping&quot; procedure using the appropriate &quot;.well-known&quot; URI instead. Typically, a &quot;user identifier&quot; is required for some form of user/password authentication. When a user identifier is required, clients MUST first use the &quot;mailbox&quot; portion of the calendar user address provided by the user in the case of a &quot;mailto:&quot; address and, if that results in an authentication failure, SHOULD fall back to using the &quot;local- part&quot; extracted from the &quot;mailto:&quot; address. For an &quot;http:&quot; or &quot;https:&quot; calendar user address, the &quot;userinfo&quot; portion is used as the user identifier for authentication. This is in line with the guidance outlined in Section 7 . If these user identifiers result in authentication failure, the client SHOULD prompt the user for a valid identifier. 5. Connecting to the service: * Subsequent to configuration, the client will make HTTP requests to the service. When using &quot;_caldavs&quot; or &quot;_carddavs&quot; services, a TLS negotiation is done immediately upon connection. The client MUST do certificate verification using the procedure outlined in Section&nbsp;6 of [RFC6125] in regard to verification with an SRV RR as the starting point. * The client does a &quot;PROPFIND&quot; [ RFC4918 ] request with the request URI set to the initial &quot;context path&quot;. The body of the request SHOULD include the DAV:current-user-principal [ RFC5397 ] property as one of the properties to return. Note that clients MUST properly handle HTTP redirect responses for the request. The server will use the HTTP authentication procedure outlined in [ RFC2617 ] or use some other appropriate authentication schemes to authenticate the user. * If the server returns a 404 (&quot;Not Found&quot;) HTTP status response to the request on the initial &quot;context path&quot;, clients MAY try repeating the request on the &quot;root&quot; URI &quot;/&quot; or prompt the user for a suitable path. * If the DAV:current-user-principal property is returned on the request, the client uses that value for the principal-URL of the authenticated user. With that, it can execute a &quot;PROPFIND&quot; request on the principal-URL and discover additional properties for configuration (e.g., calendar or address book &quot;home&quot; collections). Once a successful account discovery step has been done, clients SHOULD cache the service details that were successfully used (user identity, principal-URL with full scheme/host/port details) and reuse those when connecting again at a later time. If a subsequent connection attempt fails, or authentication fails persistently, clients SHOULD retry the SRV lookup and account discovery to &quot;refresh&quot; the cached data. 7 . Guidance for Service Providers Service providers wanting to offer CalDAV or CardDAV services that can be configured by clients using SRV records need to follow certain procedures to ensure proper operation. o CalDAV or CardDAV servers SHOULD be configured to allow authentication with calendar user addresses (just taking the &quot;mailbox&quot; portion of any &quot;mailto:&quot; URI) or email addresses respectively, or with &quot;user identifiers&quot; extracted from them. In the former case, the addresses MUST NOT conflict with other forms of a permitted user login name. In the latter case, the extracted &quot;user identifiers&quot; need to be unique across the server and MUST NOT conflict with any login name on the server. o Servers MUST force authentication for &quot;PROPFIND&quot; requests that retrieve the DAV:current-user-principal property to ensure that the value of the DAV:current-user-principal property returned corresponds to the principal-URL of the user making the request. o If the service provider uses TLS, the service provider MUST ensure a certificate is installed that can be verified by clients using the procedure outlined in Section&nbsp;6 of [RFC6125] in regard to verification with an SRV RR as the starting point. In particular, certificates SHOULD include SRV-ID and DNS-ID identifiers as appropriate, as described in Section 8 . o Service providers should install the appropriate SRV records for the offered services and optionally include TXT records.

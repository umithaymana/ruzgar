Sending on Behalf of the Organizer There are a number of scenarios that support the need for a &quot;Calendar User&quot; to act on behalf of the &quot;Organizer&quot; without explicit role changing. This might be the case if the CU designated as &quot;Organizer&quot; is sick or unable to perform duties associated with that function. In these cases, iTIP supports the notion of one CU acting on behalf of another. Using the &quot;SENT-BY&quot; parameter, a &quot;Calendar User&quot; could send an updated &quot;VEVENT&quot; &quot;REQUEST&quot;. In the case where one CU sends on behalf of another CU, the &quot;Attendee&quot; responses are still directed back towards the CU designated as &quot;Organizer&quot;. 3.2.2.6 . Forwarding to an Uninvited CU An &quot;Attendee&quot; invited to a &quot;VEVENT&quot; calendar component may send the &quot;VEVENT&quot; calendar component to another new CU not previously associated with the &quot;VEVENT&quot; calendar component. The current &quot;Attendee&quot; invited to the &quot;VEVENT&quot; calendar component does this by forwarding the original &quot;REQUEST&quot; method to the new CU. The new CU can send a &quot;REPLY&quot; to the &quot;Organizer&quot; of the &quot;VEVENT&quot; calendar component. The reply contains an &quot;ATTENDEE&quot; property for the new CU. The &quot;Organizer&quot; ultimately decides whether or not the new CU becomes part of the event and is not obligated to do anything with a &quot;REPLY&quot; from a new (uninvited) CU. If the &quot;Organizer&quot; does not want the new CU to be part of the event, the new &quot;ATTENDEE&quot; property is not added to the &quot;VEVENT&quot; calendar component. The &quot;Organizer&quot; MAY send the CU a &quot;CANCEL&quot; message to indicate that they will not be added to the event. If the &quot;Organizer&quot; decides to add the new CU, the new &quot;ATTENDEE&quot; property is added to the &quot;VEVENT&quot; calendar component. Furthermore, the &quot;Organizer&quot; is free to change any &quot;ATTENDEE&quot; Daboo Standards Track [Page 24] RFC 5546 iTIP December 2009 property parameter from the values supplied by the new CU to something the &quot;Organizer&quot; considers appropriate. The &quot;Organizer&quot; SHOULD send the new CU a &quot;REQUEST&quot; message to inform them that they have been added. When forwarding a &quot;REQUEST&quot; to another CU, the forwarding &quot;Attendee&quot; MUST NOT make changes to the original message. 3.2.2.7 . Updating Attendee Status The &quot;Organizer&quot; of an event may also request updated status from one or more &quot;Attendees&quot;. The &quot;Organizer&quot; sends a &quot;REQUEST&quot; method to the &quot;Attendee&quot; and sets the &quot;ATTENDEE;RSVP=TRUE&quot; property parameter. The &quot;SEQUENCE&quot; property for the event is not changed from its previous value. A recipient will determine that the only change in the &quot;REQUEST&quot; is that their &quot;RSVP&quot; property parameter indicates a request for updated status. The recipient SHOULD respond with a &quot;REPLY&quot; method indicating their current status with respect to the &quot;REQUEST&quot;. 3.2.3 . REPLY The &quot;REPLY&quot; method in a &quot;VEVENT&quot; calendar component is used to respond (e.g., accept or decline) to a &quot;REQUEST&quot; or to reply to a delegation &quot;REQUEST&quot;. When used to provide a delegation response, the &quot;Delegator&quot; SHOULD include the calendar address of the &quot;Delegate&quot; on the &quot;DELEGATED-TO&quot; property parameter of the &quot;Delegator&#x27;s&quot; &quot;ATTENDEE&quot; property. The &quot;Delegate&quot; SHOULD include the calendar address of the &quot;Delegator&quot; on the &quot;DELEGATED-FROM&quot; property parameter of the &quot;Delegate&#x27;s&quot; &quot;ATTENDEE&quot; property. The &quot;REPLY&quot; method is also used when processing of a &quot;REQUEST&quot; fails. Depending on the value of the &quot;REQUEST-STATUS&quot; property, no scheduling action may have been performed. The &quot;Organizer&quot; of an event may receive the &quot;REPLY&quot; method from a CU not in the original &quot;REQUEST&quot;. For example, a &quot;REPLY&quot; may be received from a &quot;Delegate&quot; to an event. In addition, the &quot;REPLY&quot; method may be received from an unknown CU (a &quot;Party Crasher&quot;). This uninvited &quot;Attendee&quot; may be accepted, or the &quot;Organizer&quot; may cancel the event for the uninvited &quot;Attendee&quot; by sending a &quot;CANCEL&quot; method to the uninvited &quot;Attendee&quot;. An &quot;Attendee&quot; MAY include a message to the &quot;Organizer&quot; using the &quot;COMMENT&quot; property. For example, if the user indicates tentative acceptance and wants to let the &quot;Organizer&quot; know why, the reason can be expressed in the &quot;COMMENT&quot; property value. ADD The &quot;ADD&quot; method allows the &quot;Organizer&quot; to add one or more new instances to an existing &quot;VEVENT&quot; using a single iTIP message without having to send the entire &quot;VEVENT&quot; with all the existing instance data, as it would have to do if the &quot;REQUEST&quot; method were used. The &quot;UID&quot; must be that of the existing event. If the &quot;UID&quot; property value in the &quot;ADD&quot; is not found on the recipient&#x27;s calendar, then the recipient SHOULD send a &quot;REFRESH&quot; to the &quot;Organizer&quot; in order to be updated with the latest version of the &quot;VEVENT&quot;. If an &quot;Attendee&quot; implementation does not support the &quot;ADD&quot; method, it should respond with a &quot;REQUEST-STATUS&quot; value of 3.14 and ask for a &quot;REFRESH&quot;.

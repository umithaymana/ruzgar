Recommended Practices These recommended practices should be followed in order to assure consistent handling of the following cases for an iCalendar object. 1. Content lines longer than 75 octets SHOULD be folded. 2. When the combination of the &quot;RRULE&quot; and &quot;RDATE&quot; properties in a recurring component produces multiple instances having the same start DATE-TIME value, they should be collapsed to, and considered as, a single instance. If the &quot;RDATE&quot; property is specified as a PERIOD value the duration of the recurrence instance will be the one specified by the &quot;RDATE&quot; property, and not the duration of the recurrence instance defined by the &quot;DTSTART&quot; property. 3. When a calendar user receives multiple requests for the same calendar component (e.g., REQUEST for a &quot;VEVENT&quot; calendar Desruisseaux Standards Track [Page 147] RFC 5545 iCalendar September 2009 component) as a result of being on multiple mailing lists specified by &quot;ATTENDEE&quot; properties in the request, they SHOULD respond to only one of the requests. The calendar user SHOULD also specify (using the &quot;MEMBER&quot; parameter of the &quot;ATTENDEE&quot; property) of which mailing list they are a member. 4. An implementation can truncate a &quot;SUMMARY&quot; property value to 255 octets, but it MUST NOT truncate the value in the middle of a UTF-8 multi-octet sequence. 5. If seconds of the minute are not supported by an implementation, then a value of &quot;00&quot; SHOULD be specified for the seconds component in a time value. 6. &quot;TZURL&quot; values SHOULD NOT be specified as a file URI type. This URI form can be useful within an organization, but is problematic in the Internet. 7. Some possible English values for &quot;CATEGORIES&quot; property include: &quot;ANNIVERSARY&quot;, &quot;APPOINTMENT&quot;, &quot;BUSINESS&quot;, &quot;EDUCATION&quot;, &quot;HOLIDAY&quot;, &quot;MEETING&quot;, &quot;MISCELLANEOUS&quot;, &quot;NON-WORKING HOURS&quot;, &quot;NOT IN OFFICE&quot;, &quot;PERSONAL&quot;, &quot;PHONE CALL&quot;, &quot;SICK DAY&quot;, &quot;SPECIAL OCCASION&quot;, &quot;TRAVEL&quot;, &quot;VACATION&quot;. Internationalization Considerations Applications MUST generate iCalendar streams in the UTF-8 charset and MUST accept an iCalendar stream in the UTF-8 or US-ASCII charset. 7 . Security Considerations Because calendaring and scheduling information is very privacy- sensitive, the protocol used for the transmission of calendaring and scheduling information should have capabilities to protect the information from possible threats, such as eavesdropping, replay, message insertion, deletion, modification, and man-in-the-middle attacks. As this document only defines the data format and media type of text/ calendar that is independent of any calendar service or protocol, it is up to the actual protocol specifications such as iTIP [ 2446bis ], Desruisseaux Standards Track [Page 148] RFC 5545 iCalendar September 2009 iMIP [ 2447bis ], and &quot;Calendaring Extensions to WebDAV (CalDAV)&quot; [ RFC4791 ] to describe the threats that the above attacks present, as well as ways in which to mitigate them. 8 .

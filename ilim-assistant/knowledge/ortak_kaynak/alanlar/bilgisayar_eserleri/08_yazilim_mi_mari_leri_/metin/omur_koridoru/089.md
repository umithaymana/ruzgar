CANCEL The &quot;CANCEL&quot; method in a &quot;VJOURNAL&quot; calendar component is used to send a cancellation notice of an existing journal entry. The message is sent by the &quot;Organizer&quot; of a journal entry. For a recurring journal entry, either the whole journal entry or instances of a journal entry may be cancelled. To cancel the complete range of a recurring journal entry, the &quot;UID&quot; property value for the journal entry MUST be specified and a &quot;RECURRENCE-ID&quot; property MUST NOT be specified in the &quot;CANCEL&quot; method. In order to cancel an individual instance of the journal entry, the &quot;RECURRENCE-ID&quot; property value for the journal entry MUST be specified in the &quot;CANCEL&quot; method. There are two options for canceling a sequence of instances of a recurring &quot;VJOURNAL&quot; calendar component: a. The &quot;RECURRENCE-ID&quot; property for an instance in the sequence MUST be specified with the &quot;RANGE&quot; property parameter value of &quot;THISANDFUTURE&quot; to indicate cancellation of the specified &quot;VJOURNAL&quot; calendar component and all instances after. b. Individual recurrence instances may be cancelled by specifying multiple &quot;VJOURNAL&quot; components each with a &quot;RECURRENCE-ID&quot; property corresponding to one of the instances to be cancelled. When a &quot;VJOURNAL&quot; is cancelled, the &quot;SEQUENCE&quot; property value MUST be incremented as described in Section 2.1.4 . Status Replies The &quot;REQUEST-STATUS&quot; property is used to convey status information about a &quot;REPLY&quot;, &quot;COUNTER&quot;, or &quot;DECLINECOUNTER&quot; iTIP message. The codes listed in the table below SHOULD be used. If the &quot;REQUEST- STATUS&quot; property is not present in one of these iTIP messages, then a status code of &quot;2.0&quot; (success) MUST be assumed. This specification adds a new IANA registry for &quot;REQUEST-STATUS&quot; property values, as defined in Section 7 , which includes a new registration template for defining the specific components of the &quot;REQUEST-STATUS&quot; property value. Additional codes MAY be used, provided the process described in Section&nbsp;8.2.1 of [RFC5545] is used to register them. This specification allows for multiple &quot;REQUEST-STATUS&quot; properties to be returned in iCalendar components in the appropriate iTIP messages. When multiple &quot;REQUEST-STATUS&quot; properties are present, the following restrictions apply: 1. Within any one component, the &quot;top-level&quot; numeric value of the &quot;short return status code&quot; MUST be the same for all &quot;REQUEST- STATUS&quot; properties, i.e., there cannot be a mixture of, e.g., 2.xx and 5.xx codes within a single component. 2. Across all components in the iTIP message, the following applies: A. If any one component would have a 5.xx code, then either all components MUST have a code in that range or &quot;REQUEST-STATUS&quot; MUST NOT be present in the other components if a 5.xx code is not appropriate for those components. B. Otherwise, if any one component would have a 3.xx code, then either all components MUST have a code in that range or &quot;REQUEST-STATUS&quot; MUST NOT be present in the other components if a 3.xx code is not appropriate for those components. C. 2.xx and 4.xx codes can be used in different components, provided that each component follows the restriction in (1) above.

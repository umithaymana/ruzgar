REQUEST The &quot;REQUEST&quot; method in a &quot;VEVENT&quot; component provides the following scheduling functions: o Invite &quot;Attendees&quot; to an event. o Reschedule an existing event. o Response to a &quot;REFRESH&quot; request. o Update the details of an existing event, without rescheduling it. o Update the status of &quot;Attendees&quot; of an existing event, without rescheduling it. o Reconfirm an existing event, without rescheduling it. o Forward a &quot;VEVENT&quot; to another uninvited CU. o For an existing &quot;VEVENT&quot; calendar component, delegate the role of &quot;Attendee&quot; to another CU. o For an existing &quot;VEVENT&quot; calendar component, change the role of &quot;Organizer&quot; to another CU. The &quot;Organizer&quot; originates the &quot;REQUEST&quot;. The recipients of the &quot;REQUEST&quot; method are the CUs invited to the event, the &quot;Attendees&quot;. &quot;Attendees&quot; use the &quot;REPLY&quot; method to convey attendance status to the &quot;Organizer&quot;. Daboo Standards Track [Page 20] RFC 5546 iTIP December 2009 The &quot;UID&quot; and &quot;SEQUENCE&quot; properties are used to distinguish the various uses of the &quot;REQUEST&quot; method. If the &quot;UID&quot; property value in the &quot;REQUEST&quot; is not found on the recipient&#x27;s calendar, then the &quot;REQUEST&quot; is for a new &quot;VEVENT&quot; calendar component. If the &quot;UID&quot; property value is found on the recipient&#x27;s calendar, then the &quot;REQUEST&quot; is for a rescheduling, an update, or a reconfirmation of the &quot;VEVENT&quot; calendar component. For the &quot;REQUEST&quot; method, multiple &quot;VEVENT&quot; components in a single iCalendar object are only permitted for components with the same &quot;UID&quot; property. That is, a series of recurring events may have instance-specific information. In this case, multiple &quot;VEVENT&quot; components are needed to express the entire series. Rescheduling an Event The &quot;REQUEST&quot; method may be used to reschedule an event. A rescheduled event involves a change to the existing event in terms of its time or recurrence intervals and possibly the location or description. If the recipient CUA of a &quot;REQUEST&quot; method finds that the &quot;UID&quot; property value already exists on the calendar but that the &quot;SEQUENCE&quot; (or &quot;DTSTAMP&quot;) property value in the &quot;REQUEST&quot; method is greater than the value for the existing event, then the &quot;REQUEST&quot; method describes a rescheduling of the event. Daboo Standards Track [Page 22] RFC 5546 iTIP December 2009 3.2.2.2 . Updating or Reconfirmation of an Event The &quot;REQUEST&quot; method may be used to update or reconfirm an event. An update to an existing event does not involve changes to the time or recurrence intervals, and might not involve a change to the location or description for the event. If the recipient CUA of a &quot;REQUEST&quot; method finds that the &quot;UID&quot; property value already exists on the calendar and that the &quot;SEQUENCE&quot; property value in the &quot;REQUEST&quot; is the same as the value for the existing event, then the &quot;REQUEST&quot; method describes an update of the event details, but not a rescheduling of the event. The update &quot;REQUEST&quot; method is the appropriate response to a &quot;REFRESH&quot; method sent from an &quot;Attendee&quot; to the &quot;Organizer&quot; of an event. The &quot;Organizer&quot; of an event may also send unsolicited &quot;REQUEST&quot; methods. The unsolicited &quot;REQUEST&quot; methods may be used to update the details of the event without rescheduling it, to update the &quot;PARTSTAT&quot; parameter of &quot;Attendees&quot;, or to reconfirm the event. 3.2.2.3 . Delegating an Event to Another CU Some calendar and scheduling systems allow &quot;Attendees&quot; to delegate their presence at an event to another &quot;Calendar User&quot;. iTIP supports this concept using the following workflow. Any &quot;Attendee&quot; may delegate their right to participate in a calendar &quot;VEVENT&quot; to another CU. The implication is that the delegate participates in lieu of the original &quot;Attendee&quot;, NOT in addition to the &quot;Attendee&quot;. The delegator MUST notify the &quot;Organizer&quot; of this action using the steps outlined below. Implementations may support or restrict delegation as they see fit. For instance, some implementations may restrict a delegate from delegating a &quot;REQUEST&quot; to another CU. The &quot;Delegator&quot; of an event forwards the existing &quot;REQUEST&quot; to the &quot;Delegate&quot;. The &quot;REQUEST&quot; method MUST include an &quot;ATTENDEE&quot; property with the calendar address of the &quot;Delegate&quot;. The &quot;Delegator&quot; MUST also send a &quot;REPLY&quot; method to the &quot;Organizer&quot; with the &quot;Delegator&#x27;s&quot; &quot;ATTENDEE&quot; property &quot;PARTSTAT&quot; parameter value set to &quot;DELEGATED&quot;. In addition, the &quot;DELEGATED-TO&quot; parameter MUST be included with the calendar address of the &quot;Delegate&quot;. Also, a new &quot;ATTENDEE&quot; property for the &quot;Delegate&quot; MUST be included and must specify the calendar user address set in the &quot;DELEGATED-TO&quot; parameter, as above. In response to the request, the &quot;Delegate&quot; MUST send a &quot;REPLY&quot; method to the &quot;Organizer&quot;, and optionally to the &quot;Delegator&quot;. The &quot;REPLY&quot; method SHOULD include the &quot;ATTENDEE&quot; property with the &quot;DELEGATED- FROM&quot; parameter value of the &quot;Delegator&#x27;s&quot; calendar address.

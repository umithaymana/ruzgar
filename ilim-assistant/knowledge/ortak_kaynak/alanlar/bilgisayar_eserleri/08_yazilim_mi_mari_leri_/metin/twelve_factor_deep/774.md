BeeKEM, keyhive_core , and the JS API all had to know about it, and the new approach doesn’t need any of that. It was a denial-of-service vector. Anyone could act as the “World Public” user and ask a sync server for every public document it held. Public documents are now handled one layer up, with ordinary read and relay capabilities: instead of a global “world” key, each app ships its own keys for the content it treats as public. Here’s the pattern for an “app-public” document. The app creates two principals and ships one key for each of them, so anyone running the app can read the document: An app-public document The document grants admin to its owner. Through some chain of delegations, read access is granted to an App Reader, and the App Reader grants relay to an App Fetcher. The app ships the App Reader's X25519 secret key, to decrypt with, and the App Fetcher's Ed25519 signing key, to fetch with. admin … read relay Document Owner App Reader App Fetcher shipped with the app X25519 secret key to decrypt with Ed25519 signing key to fetch with Anyone with read access to the document can set this up, not just its owner. They give the reader read access, and the reader passes relay access on to the fetcher . The app ships the reader’s X25519 secret key, so anyone with the app can decrypt as the reader, but not its signing key, so nobody can use it to change the document or its membership. It also ships the fetcher’s Ed25519 signing key, so anyone with the app can sign in to the sync server as the fetcher and pull ciphertext, which on its own they can’t read. Put the two together and you get read-only access for that app’s users. These keys aren’t really secret: anyone who downloads the app can extract them. What you get is read-only access that’s opt-in and scoped to one app. Unlike the old “World Public” user, the fetcher can only pull the documents that were made public to that app, and sync servers still only ever see ciphertext.

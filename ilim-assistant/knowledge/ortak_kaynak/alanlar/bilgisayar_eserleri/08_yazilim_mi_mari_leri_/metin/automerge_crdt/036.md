In October, Fintan Halpenny built the next step on top of that: hiding an author’s changes from your view of a document ( #1581 ). It’s on main now and will ship in the next release. import * as Automerge from "@automerge/automerge" // Hide everything `author` wrote after `heads` doc = Automerge . maskAuthor ( doc , author , heads ) Automerge . isAuthorMasked ( doc , author ) // true // ...and bring it back doc = Automerge . revealAuthor ( doc , author ) The point at which the author is cut off is called a write frontier . Changes from that author up to the frontier stay visible, and anything after it is hidden. Masking doesn’t delete anything or move the document’s heads. It only changes what your replica shows, so you can undo it with revealAuthor . We built this for Keyhive revocation. When Keyhive revokes someone’s access to a document, Automerge can stop showing the changes they made after that point, even if those changes still reach you through sync. We think masking is useful well beyond access control. For example, you could hide edits from a misbehaving bot or AI agent, review someone’s changes before accepting them, or see what a document looks like without one collaborator’s contributions. If you have other ideas, we’d love to hear them! Alex Good also made masking work when you only have part of the write frontier ( #1595 ). Your replica no longer has to wait for every head before it can show the changes you do have. Fintan made this fast too. Masked reads use Automerge’s indexes instead of scanning the whole document, and loading skips the reindex step when the mask hides nothing. Property tests check that patches and hydrated documents agree under every mask. In early November it graduated to a proper alpha: v3.0.0-alpha.1 is on npm under the next tag. What’s new: A simpler core. The old scheduler is gone. Each document now owns its own state, and the Repo just maps document IDs to documents. New APIs. Repo.query() returns an observable you can subscribe to, and DocHandle.hasHeads checks whether a document has reached some heads. DocHandle.changeAt now returns a Promise of the new heads. 32-byte document IDs. Existing 16-byte IDs still work in URLs. Faster loading. Each document loads with a single storage read, and many documents load in parallel. New benchmarks cover large imports, long text histories, and documents with many authors. Clearer failures. If a write fails, the repo stops and reports it, instead of retrying silently. Edits are now stored as loose commits and compacted later. This is an alpha: it’s not ready for production yet, and the API may still change. If you try it, we’d love to hear how it goes in the Discord ! 🗝️🐝 Keyhive Keyhive is our access control and encryption layer for Automerge and other CRDTs. This was a big month for Keyhive: a lot of work that’s been happening behind the scenes finally landed! In short: a new authority graph (Keyline), sturdier group keys, causal encryption, a canonical custom codec (heading for a stable format), no more “World Public” user, and Keyhive 0.6 running in automerge-repo-keyhive. Everything below ships in @keyhive/keyhive v0.6.0 and keyhive_core v0.10.0 . Keyline Keyline is Keyhive’s new authority graph. It used to live directly in keyhive_core , but we split it out into its own crate for symmetry with BeeKEM ( #230 ), and Keyhive’s membership now runs on it ( #288 ). As before, it is a set of signed certificates over keys: delegations that give a key some power over a subject, and revocations that withdraw a delegation. There’s a detailed design , including the alternatives we rejected and the edge cases. Unlike the prior authority graph, capabilities are now bound late (when they’re used) rather than early (at delegation time). That idea was inspired by UCAN , and it’s a natural fit for a causally consistent system. Keyline also replaces our old answer to the “dueling admins” problem. Previously, when two admins revoked each other concurrently, Keyhive broke the tie with a deterministic but arbitrary order (seniority, then causal depth, then hash), which was hard to predict. Keyline’s rules are simpler and explicit: you can never revoke the branch of the graph you’re standing on, and when peers revoke each other, both revocations stand. Below the root role, you recover by rotating the role. A duel inside the root role can’t be undone, so keep that role small. One of the interesting things about Keyline is that it has clear semantics and can be implemented in terms of SQL, Datalog, or DBSP. The first version is a fully in-memory implementation, but we plan to use databases for things like sync servers in the future. Keyline is also no_std and builds for Wasm. Its interface is async, so a backend can use a database, and signing can happen behind WebCrypto or a hardware key. Expect an Ink &amp; Switch lab note all about Keyline in the near future! CGKA Hardening John Mumm continued hardening BeeKEM , Keyhive’s group key agreement, building on the work from September . For apps, that means membership changes made concurrently by different people now merge cleanly ( #252 , #256 , #305 , #306 ), every key operation is checked against the certificates that authorize it ( #295 , #302 , #303 ), and newly invited members can decrypt a document right away ( #262 ). BeeKEM also stays consistent when signing fails or a secret is wrong, and refuses to record secrets it hasn’t verified ( #263 , #293 ). Causal Encryption John Mumm moved content encryption into its own crate, keyhive_content ( #313 ), and exposed causal encryption to both Rust and JS clients ( #317 ). Every encrypted block carries the keys of its direct causal ancestors. If you can open one point in a document’s history, you can walk back from there and open everything before it, so a new member can read the full history without anyone having to hand over a pile of old keys. In JS, that’s tryEncrypt (passing the predecessors) and tryCausalDecrypt . The design doc covers the trade-offs, including why this gives post-compromise security but not forward secrecy. Causal encryption Four encrypted blocks, each holding some content. Block D also holds the keys for blocks B and C, which each hold the key for block A, which has no ancestors. Holding the key for D is enough to open B and C, and through them A. Block A Block B Block C Block D no ancestors 🗝️ A 🗝️ A 🗝️ B 🗝️ C 🗝️ D your key content 🗝️ a parent's key unlocks The format got stricter along the way. Encrypted content is now chunked with a checked nonce ( #297 ), every block body is an envelope ( #322 ), and an ancestor key must actually be able to decrypt the content it’s listed with ( #323 ). Canonical Encoding Brooke Zelenka has been finalizing Keyhive’s custom codec, with two goals: dropping bincode and serde ( #299 , #310 , #311 ), and reaching a stable byte format we can commit to, since Keyhive data is signed, hashed, synced, and stored for the long term. Getting the bytes right matters for security too. keyhive_codec guarantees that each value has exactly one valid encoding, so a peer can’t send the same certificate under two different hashes and slip past a revocation that names one of them. Every key derivation and every signed piece of application data also gets its own context now ( #296 , #309 ), so a key or signature made for one purpose can’t be passed off as another.

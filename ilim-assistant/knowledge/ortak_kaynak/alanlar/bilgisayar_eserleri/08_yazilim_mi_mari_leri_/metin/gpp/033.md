As long as you can reliably do all of your game processing and rendering in less than that time, you can run at a steady frame rate. All you do is process the frame and then wait until it&#8217;s time for the next one, like so: The code looks a bit like this: 1000 ms / FPS = ms per frame . while ( true ) { double start = getCurrentTime (); processInput (); update (); render (); sleep ( start + MS_PER_FRAME - getCurrentTime ()); } The sleep() here makes sure the game doesn&#8217;t run too fast if it processes a frame quickly. It doesn&#8217;t help if your game runs too slowly . If it takes longer than 16ms to update and render the frame, your sleep time goes negative . If we had computers that could travel back in time, lots of things would be easier, but we don&#8217;t. Instead, the game slows down. You can work around this by doing less work each frame&#8202;&mdash;&#8202;cut down on the graphics and razzle dazzle or dumb down the AI. But that impacts the quality of gameplay for all users, even ones on fast machines. One small step, one giant step Let&#8217;s try something a bit more sophisticated. The problem we have basically boils down to: Each update advances game time by a certain amount. It takes a certain amount of real time to process that. If step two takes longer than step one, the game slows down. If it takes more than 16 ms of processing to advance game time by 16ms, it can&#8217;t possibly keep up. But if we can advance the game by more than 16ms of game time in a single step, then we can update the game less frequently and still keep up. The idea then is to choose a time step to advance based on how much real time passed since the last frame. The longer the frame takes, the bigger steps the game takes. It always keeps up with real time because it will take bigger and bigger steps to get there. They call this a variable or fluid time step. It looks like: double lastTime = getCurrentTime (); while ( true ) { double current = getCurrentTime (); double elapsed = current - lastTime ; processInput (); update ( elapsed ); render (); lastTime = current ; } Each frame, we determine how much real time passed since the last game update ( elapsed ). When we update the game state, we pass that in. The engine is then responsible for advancing the game world forward by that amount of time. Say you&#8217;ve got a bullet shooting across the screen. With a fixed time step, in each frame, you&#8217;ll move it according to its velocity. With a variable time step, you scale that velocity by the elapsed time . As the time step gets bigger, the bullet moves farther in each frame. That bullet will get across the screen in the same amount of real time whether it&#8217;s twenty small fast steps or four big slow ones. This looks like a winner: The game plays at a consistent rate on different hardware. Players with faster machines are rewarded with smoother gameplay. But, alas, there&#8217;s a serious problem lurking ahead: we&#8217;ve made the game non-deterministic and unstable. Here&#8217;s one example of the trap we&#8217;ve set for ourselves: &#8220;Deterministic&#8221; means that every time you run the program, if you give it the same inputs, you get the exact same outputs back. As you can imagine, it&#8217;s much easier to track down bugs in deterministic programs&#8202;&mdash;&#8202;find the inputs that caused the bug the first time, and you can cause it every time. Computers are naturally deterministic; they follow programs mechanically. Non-determinism appears when the messy real world creeps in. For example, networking, the system clock, and thread scheduling all rely on bits of the external world outside of the program&#8217;s control. Say we&#8217;ve got a two-player networked game and Fred has some beast of a gaming machine while George is using his grandmother&#8217;s antique PC. That aforementioned bullet is flying across both of their screens. On Fred&#8217;s machine, the game is running super fast, so each time step is tiny. We cram, like, 50 frames in the second it takes the bullet to cross the screen. Poor George&#8217;s machine can only fit in about five frames. This means that on Fred&#8217;s machine, the physics engine updates the bullet&#8217;s position 50 times, but George&#8217;s only does it five times. Most games use floating point numbers, and those are subject to rounding error . Each time you add two floating point numbers, the answer you get back can be a bit off. Fred&#8217;s machine is doing ten times as many operations, so he&#8217;ll accumulate a bigger error than George. The same bullet will end up in different places on their machines. This is just one nasty problem a variable time step can cause, but there are more. In order to run in real time, game physics engines are approximations of the real laws of mechanics. To keep those approximations from blowing up , damping is applied. That damping is carefully tuned to a certain time step. Vary that, and the physics gets unstable. &#8220;Blowing up&#8221; is literal here. When a physics engine flakes out, objects can get completely wrong velocities and launch themselves into the air. This instability is bad enough that this example is only here as a cautionary tale and to lead us to something better&#8230; Play catch up One part of the engine that usually isn&#8217;t affected by a variable time step is rendering . Since the rendering engine captures an instant in time, it doesn&#8217;t care how much time advanced since the last one. It renders things wherever they happen to be right then. This is more or less true. Things like motion blur can be affected by time step, but if they&#8217;re a bit off, the player doesn&#8217;t usually notice. We can use this fact to our advantage. We&#8217;ll update the game using a fixed time step because that makes everything simpler and more stable for physics and AI. But we&#8217;ll allow flexibility in when we render in order to free up some processor time. It goes like this: A certain amount of real time has elapsed since the last turn of the game loop. This is how much game time we need to simulate for the game&#8217;s &#8220;now&#8221; to catch up with the player&#8217;s. We do that using a series of fixed time steps. The code looks a bit like: double previous = getCurrentTime (); double lag = 0.0 ; while ( true ) { double current = getCurrentTime (); double elapsed = current - previous ; previous = current ; lag += elapsed ; processInput (); while ( lag &gt;= MS_PER_UPDATE ) { update (); lag -= MS_PER_UPDATE ; } render (); } There&#8217;s a few pieces here. At the beginning of each frame, we update lag based on how much real time passed. This measures how far the game&#8217;s clock is behind compared to the real world. We then have an inner loop to update the game, one fixed step at a time, until it&#8217;s caught up. Once we&#8217;re caught up, we render and start over again. You can visualize it sort of like this: Note that the time step here isn&#8217;t the visible frame rate anymore. MS_PER_UPDATE is just the granularity we use to update the game. The shorter this step is, the more processing time it takes to catch up to real time. The longer it is, the choppier the gameplay is. Ideally, you want it pretty short, often faster than 60 FPS, so that the game simulates with high fidelity on fast machines. But be careful not to make it too short. You need to make sure the time step is greater than the time it takes to process an update() , even on the slowest hardware. Otherwise, your game simply can&#8217;t catch up. I left it out here, but you can safeguard this by having the inner update loop bail after a maximum number of iterations. The game will slow down then, but that&#8217;s better than locking up completely. Fortunately, we&#8217;ve bought ourselves some breathing room here. The trick is that we&#8217;ve yanked rendering out of the update loop . That frees up a bunch of CPU time. The end result is the game simulates at a constant rate using safe fixed time steps across a range of hardware. It&#8217;s just that the player&#8217;s visible window into the game gets choppier on a slower machine. Stuck in the middle There&#8217;s one issue we&#8217;re left with, and that&#8217;s residual lag. We update the game at a fixed time step, but we render at arbitrary points in time. This means that from the user&#8217;s perspective, the game will often display at a point in time between two updates. Here&#8217;s a timeline: As you can see, we update at a nice tight, fixed interval. Meanwhile, we render whenever we can. It&#8217;s less frequent than updating, and it isn&#8217;t steady either. Both of those are OK. The lame part is that we don&#8217;t always render right at the point of updating. Look at the third render time. It&#8217;s right between two updates: Imagine a bullet is flying across the screen. On the first update, it&#8217;s on the left side. The second update moves it to the right side. The game is rendered at a point in time between those two updates, so the user expects to see that bullet in the center of the screen. With our current implementation, it will still be on the left side. This means motion looks jagged or stuttery. Conveniently, we actually know exactly how far between update frames we are when we render: it&#8217;s stored in lag . We bail out of the update loop when it&#8217;s less than the update time step, not when it&#8217;s zero . That leftover amount? That&#8217;s how far into the next frame we are. When we go to render, we&#8217;ll pass that in: render ( lag / MS_PER_UPDATE ); We divide by MS_PER_UPDATE here to normalize the value. The value passed to render() will vary from 0 (right at the previous frame) to just under 1.0 (right at the next frame), regardless of the update time step.

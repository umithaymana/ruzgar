The component IDs under the components ( cmps ) key, including those of the child devices, are used as part of the discovery identification and must be unique within the payload. A platform ( p ) config option is required for each component config that is added to identify the component platform. Also required is a unique_id for entity-based components. To remove the components, publish an empty (retained) string payload to the discovery topic. This will remove all components of the device, including disabled entities, and clear the published discovery payload. It will also remove the device entry if there are no further references to it. Removing the device in Home Assistant also clears the published device discovery payload. Removing a child device in Home Assistant only removes the child device and its entities, and the parent device when it has no other components or child devices left. The published device discovery payload is not cleared, so the child device and its components are added again when a new device discovery payload is received. To prevent this, remove the child device from the device discovery payload. An empty config can be published as an update to remove a single component from the device discovery. An empty payload published to its old single component discovery topic, for example after a migration to device discovery , does not remove it. When an entity that was discovered through device discovery is removed from Home Assistant, the device discovery payload is not cleared, as that would remove all components of the device. The entity will be added again when a device discovery payload is received that still contains the component. To prevent this, disable the entity instead, or remove the component from the device discovery payload as described above. A component config part in a device discovery payload must have the platform ( p ) option set with the name of the component and also must have at least one component specific config option. Entity components must have set the unique_id option and have a device context. The component IDs must be unique across the device and its child devices. Migration from single component to device discovery To allow a smooth migration from single component discovery to device discovery: Ensure all entities have a unique_id and a device context. Move the object_id inside the discovery payload, if that is available, or use a unique ID or the component. Consider using the previous node_id as the new object_id of the device discovery topic. Ensure the unique_id matches and the device context has the correct identifiers. Send the following payload to all existing single component discovery topics: {"migrate_discovery": true } . This will unload the discovered item, but its settings will be retained. Switch the discovery topic to the device discovery topic and include all the component configurations. Clean up the single component discovery messages with an empty payload. This clears the retained messages at the broker, but does not remove the migrated components. During the migration steps, INFO messages will be logged to inform you about the progress of the migration. Important Consider testing the migration process in a non-production environment before applying it to a live system. Single component discovery payload When using single component discovery messages, the &lt;component&gt; part in the discovery topic must be one of the supported MQTT platforms. The options in the payload are only used to set up one specific component. If a device contains multiple components, it is recommended to use device discovery instead. MQTT entities can share device configuration, meaning one entity can include the full device configuration and other entities can link to that device by only setting the shared identifiers or connections . It is recommended to also include the device name . See MQTT device configuration .

When discovered items are removed, a parent device is kept as long as it has child devices, and is removed after its last child device when no other items use it. When the identifiers of an existing MQTT device are used for a child device, the existing device is converted into a child device. It keeps its device ID, so automations that use the device keep working. If the existing device is still in use as a regular device, the conversion fails. An entity with that child device is then not added, and an error is logged. With a discovery update, the update is canceled, the entity keeps its current configuration and device, and a warning is logged. In that case, update the configuration of all items that use the device, and reload the MQTT integration. A child device can’t be moved to another parent device. When the parent device of a child device changes, the same happens as when a conversion fails. To move a child device to another parent device, remove the child device in Home Assistant, and reload the MQTT integration. The child device is then added again with its new parent device, and keeps its device ID. With single component discovery, removing the child device can also clear the discovery payloads of its entities. The publisher then has to send them again. Device configuration in YAML Add a device mapping to the configuration of each entity that is part of the device. In the example below, both sensors are linked to the same device: mqtt : - sensor : name : " Temperature" unique_id : " bedroom_temperature" state_topic : " home/bedroom/temperature" device : identifiers : " bedroom01" name : " Bedroom" manufacturer : " Bla electronics" model : " xya" - sensor : name : " Humidity" unique_id : " bedroom_humidity" state_topic : " home/bedroom/humidity" device : identifiers : " bedroom01" name : " Bedroom" To link an entity to a child device , add a child_device mapping to the device mapping. In the example below, the switch is linked to the child device Outlet 1 , which is a part of the power strip. The power sensor is linked to the power strip itself: mqtt : - switch : name : " Switch" unique_id : " power_strip_outlet_1_switch" command_topic : " power_strip/outlet_1/set" device : identifiers : " power_strip" name : " Power strip" manufacturer : " Bla electronics" child_device : identifiers : " power_strip_outlet_1" name : " Outlet 1" - sensor : name : " Power" unique_id : " power_strip_power" state_topic : " power_strip/power" device_class : power unit_of_measurement : " W" device : identifiers : " power_strip" name : " Power strip" Device configuration with device discovery With device discovery , the device ( dev ) mapping is required and is set once, at the root of the discovery payload. It applies to all components in the payload and can’t be overridden per component. Entity components must have a unique_id . Child devices are listed in child_devices , which can be abbreviated as cdevs . Each child device has identifiers , an optional name , and its own components ( cmps ), which link to the child device. The device’s components are listed in components at the root of the discovery payload, which is optional when child devices are listed. A child_device mapping is not allowed in the device mapping at the root of the discovery payload. Only entity components can be part of a child device, device triggers and tags can’t. The component IDs must be unique across the device and its child devices, as they identify each component. The identifiers of a child device must be unique, and must differ from the identifiers of the device. The shared options at the root of the discovery payload, like origin and the availability options, also apply to the components of the child devices. In the example below, each switch is linked to a child device of the power strip, and the power sensor is linked to the power strip itself: { "dev" : { "ids" : "power_strip" , "name" : "Power strip" , "mf" : "Bla electronics" }, "o" : { "name" : "bla2mqtt" }, "cdevs" : [ { "ids" : "power_strip_outlet_1" , "name" : "Outlet 1" , "cmps" : { "outlet_1" : { "p" : "switch" , "name" : "Switch" , "uniq_id" : "power_strip_outlet_1_switch" , "cmd_t" : "power_strip/outlet_1/set" } } }, { "ids" : "power_strip_outlet_2" , "name" : "Outlet 2" , "cmps" : { "outlet_2" : { "p" : "switch" , "name" : "Switch" , "uniq_id" : "power_strip_outlet_2_switch" , "cmd_t" : "power_strip/outlet_2/set" } } } ], "cmps" : { "power" : { "p" : "sensor" , "name" : "Power" , "uniq_id" : "power_strip_power" , "stat_t" : "power_strip/power" , "dev_cla" : "power" , "unit_of_meas" : "W" } } } A component can be moved between the device and its child devices, or between child devices, by moving it to another components mapping with the same component ID. To remove a component of a child device, send the component with only its platform option, as for the other components. Device configuration with single component discovery With single component discovery , the device ( dev ) mapping is added to the discovery payload of each component that is part of the device. For device triggers, the device mapping is required. Device triggers and tags don’t need a unique_id . To link an entity to a child device , add a child_device ( cdev ) mapping to the device mapping, the same way as in YAML. In the example below, the switch is linked to the child device Outlet 1 , which is a part of the power strip. Device configuration with subentries Each subentry holds one MQTT device. The device details are set in the UI when the subentry is added or reconfigured. Child devices are not supported for subentries. Device configuration options Configuration Variables Looking for your configuration file? device map ( Optional ) Information about the device to tie an MQTT entity, device trigger, or tag into the device registry . At least one of identifiers or connections must be set to identify the device. configuration_url string ( Optional ) A link to the webpage that can manage the configuration of this device. Can be either an http:// , https:// , or an internal homeassistant:// URL. connections list ( Optional ) A list of connections of the device to the outside world as a list of tuples [connection_type, connection_identifier] . For example, the MAC address of a network interface: "connections": [["mac", "02:5b:26:a8:dc:12"]] . hw_version string ( Optional ) The hardware version of the device. identifiers string | list ( Optional ) A list of IDs that uniquely identify the device. For example, a serial number. manufacturer string ( Optional ) The manufacturer of the device. model string ( Optional ) The model of the device. model_id string ( Optional ) The model identifier of the device. name string ( Optional ) The name of the device. serial_number string ( Optional ) The serial number of the device. child_device map ( Optional ) The child device of the device the entity is linked to. Requires a unique_id . Not supported for device triggers and tags. With device discovery, child devices are listed in child_devices instead, see device configuration with device discovery . identifiers string | list Required A list of IDs that uniquely identify the child device. name string ( Optional ) The name of the child device. suggested_area string ( Optional ) Suggest an area if the device isn’t in one yet. sw_version string ( Optional ) The firmware version of the device. via_device string ( Optional ) Identifier of a device that routes messages between this device and Home Assistant, like a hub or a bridge. This is used to show the device topology in Home Assistant. Use a child device for a part of a physical device instead. A child device can’t be used as via_device . Grouping entities If the MQTT entity represents a group of other entities, the member entities can be made visible in the UI by setting the list of unique IDs of the member entities in the group configuration option of the entity group: group A list of unique IDs of the member entities. Set this if the entity represents a group entity. Note that the member entities must be already configured before the member entities will become visible in the UI at the moment a group entity is loaded. MQTT Discovery The discovery of MQTT devices will enable one to use MQTT devices with only minimal configuration effort on the side of Home Assistant. The configuration is done on the device itself and the topic used by the device. Similar to the HTTP binary sensor and the HTTP sensor . To prevent multiple identical entries if a device reconnects, a unique identifier is necessary. Two parts are required on the device side: The configuration topic, and the device configuration as payload. MQTT discovery is enabled by default and the subscriptions to perform the discovery are done at Quality of Service level 0 by default. The default prefix for the discovery topic is homeassistant .

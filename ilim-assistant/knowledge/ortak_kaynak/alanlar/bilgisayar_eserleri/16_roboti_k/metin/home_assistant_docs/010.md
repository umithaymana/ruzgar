[Learn more] is the part of an automation or script that makes something happen, for example, turning on a light, sending a notification, or activating a scene . When a trigger starts an automation and its conditions are met, the automation runs its actions. A script runs its actions when you start it. Automations and scripts use the same actions. Each action does one thing. For example, Turn on light turns on lights. For a description of all actions, refer to the list of available actions . Some actions control automations themselves, for example, to turn off another automation. For these actions, refer to Actions for automations . Parts of an action Many actions have some of the following parts: Targets: what the action controls, for example, the lights in the living room. For details, refer to Action targets . Options: details of what the action does, for example, the brightness of the lights. For details, refer to Action options . Response data: what the action returns, for example, the calendar events of the next week. For details, refer to Action response data . Actions run in order An automation or script runs its actions one after the other, from top to bottom. As a result: If a condition between the actions isn’t met, the actions after the condition don’t run. For details, refer to Condition . If an action fails, the actions after the failed action don’t run. To continue anyway, refer to Continuing when a step fails . Actions don’t run at the same time. To run actions at the same time, use Run in parallel . Actions and building blocks Building blocks control whether, when, and in which order the actions run. For example, a building block can check a condition, wait a few seconds, repeat steps, or choose between steps. To add a building block in the editor, select Add action , and then select Blocks . For how steps run, refer to Building blocks . For all building blocks, refer to the list of building blocks . Built-in actions Most actions come from integrations. Two actions are built into automations and scripts : Fire manual event : Lets one automation tell another that something happened. Set conversation response : Sets what Assist says after a sentence trigger. Built-in actions only work as steps in an automation or script. You can’t run them directly from Settings &gt; Tools &gt; Actions or from a dashboard button, and they don’t have targets. Adding an action in the editor Go to Settings &gt; Automations &amp; scenes and select an automation. To edit a script, go to the Scripts tab and select the script. In the Then do section of an automation, or the Sequence section of a script, select Add action . Search for and select the action, for example, Turn on light . You can also first select what you want to control under By target , and then select the action. If the action has targets, select what it should control under Targets . For details, refer to Action targets . Fill in the other options of the action. For details, refer to Action options . Select Save . Adding an action in YAML In YAML, use action with the name of the action, and optionally target and data . To give the action a name, use alias . In the editor, you set the same name with Menu &gt; Rename . For details, refer to Renaming a trigger, condition, or action . Under Targets , you can select entities, devices, areas, floors, and labels, or a combination of these. When you select an area, a floor, or a label, the action controls the matching entities that support it. For example, if Turn on light targets an area, all lights in that area turn on. To learn which entities are part of a target, refer to Automation targets . To leave out some of them, for example, all lights in an area except one, refer to Excluding targets . In YAML, enter what the action controls under target . The target contains at least one of the following: entity_id , device_id , area_id , floor_id , or label_id . Each of these can be a list. Use the IDs in lowercase, not the names. To leave out some entities, add an exclude block. For details and an example, refer to Targets in YAML . This data is called action response data . Actions return response data for information that is dynamic or large, and that doesn’t fit well in an entity state. For example, response data can be the upcoming calendar events for the next week, or detailed driving directions. To use the response data, store it in a variable . You can choose any name for the variable. In the editor, actions that return data show a Response variable field. If the field has a checkbox next to it, select the checkbox first. Then enter the name of the variable. In YAML, use response_variable . The following example stores the calendar events of the next 24 hours in the variable agenda . For example, calendar.get_events returns the events of a calendar. For these actions, the response variable is required. If you leave it out, the action fails when it runs, and the automation or script stops. Some actions can return data. For example, conversation.process can return the reply of the conversation agent. For these actions, the response variable is optional. If you set it, the data is stored in the variable. If you leave it out, the action still runs, but its data isn’t stored. Most actions don’t return data. In the editor, they don’t show a Response variable field. If you add response_variable to one of these actions in YAML, the action fails when it runs, and the automation or script stops. To find out whether an action returns data, add the action to an automation or script in its editor. If the action returns data, it shows a Response variable field.

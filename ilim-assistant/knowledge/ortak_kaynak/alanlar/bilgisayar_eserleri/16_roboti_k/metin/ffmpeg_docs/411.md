The sidecar is a sequence of records, one per encoded JPEG, in encode order: u32be length u8 payload[length] length does not include the 4-byte prefix and must not exceed 16 MiB. A zero length leaves that packet unchanged. A non-empty payload must be a concatenation of complete APP segments ( FF En plus the 16-bit length that includes those two length bytes). If the payload starts with APP0 and the packet has an APP0 marker in the two bytes immediately following SOI, that APP0 segment is dropped. APP0 segments preceded by fill bytes or another segment are retained. An APP1-only payload keeps the encoder APP0: SOI, APP1, APP0, DQT, ... The filter requires sidecar . Extra unused sidecar bytes are ignored; a packet without a matching record is an error. Records follow packets in arrival order. Flushing the filter does not rewind the sidecar, so a reused context needs a sidecar positioned for the packets it will see next. A sidecar read or validation error prevents further record consumption by that filter context. To resume, create a new context with a sidecar matching the remaining packets. Flushing does not clear this error. ffmpeg -i in.mp4 -c:v mjpeg -bsf:v jpegapp=sidecar=00000004DEADBEEF frame_%d.jpg 18.21 mjpeg2jpeg # TOC Convert MJPEG/AVI1 packets to full JPEG/JFIF packets. MJPEG is a video codec wherein each video frame is essentially a JPEG image. The individual frames can be extracted without loss, e.g. by ffmpeg -i ../some_mjpeg.avi -c:v copy frames_%d.jpg Unfortunately, these chunks are incomplete JPEG images, because they lack the DHT segment required for decoding. Quoting from http://www.digitalpreservation.gov/formats/fdd/fdd000063.shtml : Avery Lee, writing in the rec.video.desktop newsgroup in 2001, commented that &quot;MJPEG, or at least the MJPEG in AVIs having the MJPG fourcc, is restricted JPEG with a fixed &ndash; and *omitted* &ndash; Huffman table. The JPEG must be YCbCr colorspace, it must be 4:2:2, and it must use basic Huffman encoding, not arithmetic or progressive. . . . You can indeed extract the MJPEG frames and decode them with a regular JPEG decoder, but you have to prepend the DHT segment to them, or else the decoder won&rsquo;t have any idea how to decompress the data. The exact table necessary is given in the OpenDML spec.&quot; This bitstream filter patches the header of frames extracted from an MJPEG stream (carrying the AVI1 header ID and lacking a DHT segment) to produce fully qualified JPEG images. ffmpeg -i mjpeg-movie.avi -c:v copy -bsf:v mjpeg2jpeg frame_%d.jpg exiftran -i -9 frame*.jpg ffmpeg -i frame_%d.jpg -c:v copy rotated.avi 18.22 mjpegadump # TOC Add an MJPEG A header to the bitstream, to enable decoding by Quicktime. 18.23 mov2textsub # TOC Extract a representable text file from MOV subtitles, stripping the metadata header from each subtitle packet.

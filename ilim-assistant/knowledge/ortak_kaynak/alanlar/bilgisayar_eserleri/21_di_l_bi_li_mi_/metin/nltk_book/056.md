Much of the interesting work in building a classifier is deciding what features might be relevant, and how we can represent them. Although it's often possible to get decent performance by using a fairly simple and obvious set of features, there are usually significant gains to be had by using carefully constructed features based on a thorough understanding of the task at hand. Typically, feature extractors are built through a process of trial-and-error, guided by intuitions about what information is relevant to the problem. It's common to start with a &quot;kitchen sink&quot; approach, including all the features that you can think of, and then checking to see which features actually are helpful. We take this approach for name gender features in 1.2 . &nbsp; def gender_features2 (name): features = {} features[ &quot;first_letter&quot; ] = name[0].lower() features[ &quot;last_letter&quot; ] = name[-1].lower() for letter in 'abcdefghijklmnopqrstuvwxyz' : features[ &quot;count({})&quot; .format(letter)] = name.lower().count(letter) features[ &quot;has({})&quot; .format(letter)] = (letter in name.lower()) return features &nbsp; &gt;&gt;&gt; gender_features2( 'John' ) {'count(j)': 1, 'has(d)': False, 'count(b)': 0, ...} Example 1.2 (code_gender_features_overfitting.py) : Figure 1.2 : A Feature Extractor that Overfits Gender Features. The feature sets returned by this feature extractor contain a large number of specific features, leading to overfitting for the relatively small Names Corpus. However, there are usually limits to the number of features that you should use with a given learning algorithm &#8212; if you provide too many features, then the algorithm will have a higher chance of relying on idiosyncrasies of your training data that don't generalize well to new examples. This problem is known as overfitting , and can be especially problematic when working with small training sets.

For example, suppose that we are looking for the value for a particular path P in nb-NO . In the absence of aliases, normally the following lookup is used. nb-NO → nb → root That is, we first look in nb-NO . If there is no value for P there, then we look in nb . If there is no value for P there, we return the value for P in root (or a code value, if there is nothing there). Remember that if there is an alias element along this path, then the lookup may restart with a different path in nb-NO (or another locale). However, suppose that nb-NO has the fallback values [nn da sv en] , derived from language matching. In that case, an implementation may progressively look up each of the listed locales, with the appropriate substitutions, returning the first value that is not found in root . This follows roughly the following pseudocode: value = lookup(P, nb-NO); if (locationFound != root) return value; value = lookup(P, nn-NO); if (locationFound != root) return value; value = lookup(P, da-NO); if (locationFound != root) return value; value = lookup(P, sv-NO); if (locationFound != root) return value; value = lookup(P, en-NO); return value; The locales in the fallback list are not used recursively. For example, for the lookup of a path in nb-NO, if fr were a fallback value for da , it would not matter for the above process. Only the original locale matters. The language matching data is intended to be used according to the following algorithm. This is a logical description, and can be optimized for production in many ways. In this algorithm, the languageMatching data is interpreted as an ordered list. Distances between given pair of subtags can be larger or smaller than the typical distances. For example, the distance between en and en-GB can be greater than those between en-GB and en-IE. In some cases, language subtag and/or script subtag differences can be as small as the typical region difference. (Example: sr-Latn vs. sr-Cyrl). The distances resulting from the table are not linear, but are rather chosen to produce expected results. So a distance of 10 is not necessarily twice as "bad" as a distance of 5. Implementations may want to have a mode where script distances should swamp language distances. The tables are built such that this can be accomplished by increasing the language distance by 4x. The language matching algorithm takes a list of a user’s desired locales, and a list of the application’s supported locales. That avoids the following problem: Supported locales: "de, fr, ja" User's desired locales: "de-AT, fr" This user would expect to get "de", not "fr". In practice, when a user selects a list of preferred locales, they don't include all the regional variants ahead of their second base locale. Yet while the user's desired locales really doesn't tell us the priority ranking among their locales, normally the fall-off between the user's locales is substantially greater than regional variants. But unless F is greater than the distance between de-AT and de-DE, then the user’s second-choice locale would be returned. The base language subtag "und" is a special case. Suppose we have the following situation: desired locales: {und, it} supported locales: {en, it} resulting locale: en Part of this is because 'und' has a special function in BCP 47; it stands in for 'no supplied base language'. To prevent this from happening, if the desired base language is und, the language matcher should not apply likely subtags to it. The first match is with "*-*-*", for a match of 96%. The locales are truncated to nn-Latn and nb-Latn, then to nn and nb. The first match is also for a value of 96%, so the result is 92%. Note that language matching is orthogonal to the how closely two locales are related linguistically. For example, Breton is more closely related to Welsh than to French, but French is the better match (because it is more likely that a Breton reader will understand French than Welsh). This also illustrates that the matches are often asymmetric: it is not likely that a French reader will understand Breton. The "*" acts as a wild card, as shown in the following example: &lt;languageMatch desired="es-*-ES" supported="es-*-ES" percent="100" /&gt; &lt;!-- Latin American Spanishes are closer to each other. Approximate by having es-ES be further from everything else. --&gt; &lt;languageMatch desired="es-*-ES" supported="es-*-*" percent="93" /&gt; &lt;languageMatch desired="*" supported="*" percent="1" /&gt; &lt;!-- [Default value - must be at end!] Normally there is no comprehension across different languages. --&gt; &lt;languageMatch desired="*-*" supported="*-*" percent="20" /&gt; &lt;!-- [Default value - must be at end!] Normally there is little comprehension across different scripts. --&gt; &lt;languageMatch desired="*-*-*" supported="*-*-*" percent="96" /&gt; &lt;!-- [Default value - must be at end!] Normally there are small differences across different regions. --&gt; When the language+region is not matched, and there is otherwise no reason to pick among the supported regions for that language, then some measure of geographic "closeness" can be used. The results may be more understandable by users. Looking for en-SK, for example, should fall back to something within Europe (eg en-GB) in preference to something far away and unrelated (eg en-SG). Such a closeness metric does not need to be exact; a small amount of data can be used to give an approximate distance between any two regions. However, any such data must be used carefully; although Hong Kong is closer to India than to the UK, it is unlikely that en-IN would be a better match to en-HK than en-GB would. Language Matching Variables A matchVariable allows the matching to take into account broad similarities that would give better results. For example, the English-speaking regions that are or inherit from US English (AS|GU|MH|MP|PR|UM|VI|US) form a “cluster”. Each region in that particular cluster should be closer to each other than to any region outside the cluster. Consequently, a region that is outside that cluster should be closer to another region that is also outside that cluster than to one that is in it. These are especially useful for the the “world languages” like English, Spanish, Portuguese, Arabic, etc. Example: &lt;languageMatches type="…"&gt; &lt;paradigmLocales locales="en en-GB es es-419 pt-BR pt-PT" /&gt; &lt;matchVariable id="$enUS" value="AS+GU+MH+MP+PR+UM+US+VI" /&gt; &lt;matchVariable id="$cnsar" value="HK+MO" /&gt; &lt;matchVariable id="$americas" value="019" /&gt; &lt;matchVariable id="$maghreb" value="MA+DZ+TN+LY+MR+EH" /&gt; &lt;languageMatch desired="no" supported="nb" distance="1" /&gt;&lt;!-- no ⇒ nb --&gt; … &lt;languageMatch desired="ar_*_$maghreb" supported="ar_*_$maghreb" distance="4" /&gt; &lt;!-- ar; *; $maghreb ⇒ ar; *; $maghreb --&gt; &lt;languageMatch desired="ar_*_$!maghreb" supported="ar_*_$!maghreb" distance="4" /&gt; &lt;!-- ar; *; $!maghreb ⇒ ar; *; $!maghreb --&gt; … The matchVariable allows for a rule to match to multiple regions, as illustrated by $maghreb . The syntax is simple: it allows for + for union and - for set difference , but no precedence. So A-B-C is interpreted as ((A-B)-C), not as (A-(B-C)). For example, if we have A={b c}, B={a c}, C={a b}, then the result is ({b c}-{a c})-{a b} = {b}-{a b} = {}, not {b c}-({a c}-{a b}) = {b c}-{c} = {b}. The variable id has a value of the form [$][a-zA-Z0-9]+. If $X is defined, then $!X automatically means all those regions that are not in $X. When the set is interpreted, then macrolanguages are (logically) transformed into a list of their contents, so “053+GB” → “AU+GB+NF+NZ”. This is done recursively, so 009 → “053+054+057+061+QO” → “AU+NF+NZ+FJ+NC+PG+SB +VU...”. Note that we use 019 for all of the Americas in the variables above, because en-US should be in the same cluster as es-419 and its contents.

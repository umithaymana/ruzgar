Watch a free video lesson on Vue School Props Declaration ​ Vue components require explicit props declaration so that Vue knows what external props passed to the component should be treated as fallthrough attributes (which will be discussed in its dedicated section ). In SFCs using &lt;script setup&gt; , props can be declared using the defineProps() macro: vue &lt; script setup &gt; const props = defineProps ([ &#39;foo&#39; ]) console. log (props.foo) &lt;/ script &gt; In non- &lt;script setup&gt; components, props are declared using the props option: js export default { props: [ &#39;foo&#39; ], setup ( props ) { // setup() receives props as the first argument. console. log (props.foo) } } Notice the argument passed to defineProps() is the same as the value provided to the props options: the same props options API is shared between the two declaration styles. Props are declared using the props option: js export default { props: [ &#39;foo&#39; ], created () { // props are exposed on `this` console. log ( this .foo) } } In addition to declaring props using an array of strings, we can also use the object syntax: js export default { props: { title: String, likes: Number } } js // in &lt;script setup&gt; defineProps ({ title: String, likes: Number }) js // in non-&lt;script setup&gt; export default { props: { title: String, likes: Number } } For each property in the object declaration syntax, the key is the name of the prop, while the value should be the constructor function of the expected type. This not only documents your component, but will also warn other developers using your component in the browser console if they pass the wrong type. We will discuss more details about prop validation further down this page. See also: Typing Component Props If you are using TypeScript with &lt;script setup&gt; , it&#39;s also possible to declare props using pure type annotations: vue &lt; script setup lang = &quot;ts&quot; &gt; defineProps &lt;{ title ?: string likes ?: number }&gt;() &lt;/ script &gt; More details: Typing Component Props Reactive Props Destructure ​ Vue&#39;s reactivity system tracks state usage based on property access. E.g. when you access props.foo in a computed getter or a watcher, the foo prop gets tracked as a dependency. So, given the following code: js const { foo } = defineProps ([ &#39;foo&#39; ]) watchEffect (() =&gt; { // runs only once before 3.5 // re-runs when the &quot;foo&quot; prop changes in 3.5+ console. log (foo) }) In version 3.4 and below, foo is an actual constant and will never change. In version 3.5 and above, Vue&#39;s compiler automatically prepends props. when code in the same &lt;script setup&gt; block accesses variables destructured from defineProps . Therefore the code above becomes equivalent to the following: js const props = defineProps ([ &#39;foo&#39; ]) watchEffect (() =&gt; { // `foo` transformed to `props.foo` by the compiler console. log (props.foo) }) In addition, you can use JavaScript&#39;s native default value syntax to declare default values for the props. This is particularly useful when using the type-based props declaration: ts const { foo = &#39;hello&#39; } = defineProps &lt;{ foo ?: string }&gt;() If you prefer to have more visual distinction between destructured props and normal variables in your IDE, Vue&#39;s VSCode extension provides a setting to enable inlay-hints for destructured props. Passing Destructured Props into Functions ​ When we pass a destructured prop into a function, e.g.: js const { foo } = defineProps ([ &#39;foo&#39; ]) watch (foo, /* ... */ ) This will not work as expected because it is equivalent to watch(props.foo, ...) - we are passing a value instead of a reactive data source to watch . In fact, Vue&#39;s compiler will catch such cases and throw a warning. Similar to how we can watch a normal prop with watch(() =&gt; props.foo, ...) , we can watch a destructured prop also by wrapping it in a getter: js watch (() =&gt; foo, /* ... */ ) In addition, this is the recommended approach when we need to pass a destructured prop into an external function while retaining reactivity: js useComposable (() =&gt; foo) The external function can call the getter (or normalize it with toValue ) when it needs to track changes of the provided prop, e.g. in a computed or watcher getter. Prop Passing Details ​ Prop Name Casing ​ We declare long prop names using camelCase because this avoids having to use quotes when using them as property keys, and allows us to reference them directly in template expressions because they are valid JavaScript identifiers: js defineProps ({ greetingMessage: String }) js export default { props: { greetingMessage: String } } template &lt; span &gt;{{ greetingMessage }}&lt;/ span &gt; Technically, you can also use camelCase when passing props to a child component (except in in-DOM templates ). However, the convention is using kebab-case in all cases to align with HTML attributes: template &lt; MyComponent greeting-message = &quot;hello&quot; /&gt; We use PascalCase for component tags when possible because it improves template readability by differentiating Vue components from native elements. However, there isn&#39;t as much practical benefit in using camelCase when passing props, so we choose to follow each language&#39;s conventions. Static vs. Dynamic Props ​ So far, you&#39;ve seen props passed as static values, like in: template &lt; BlogPost title = &quot;My journey with Vue&quot; /&gt; You&#39;ve also seen props assigned dynamically with v-bind or its : shortcut, such as in: template &lt;!-- Dynamically assign the value of a variable --&gt; &lt; BlogPost : title = &quot; post.title &quot; /&gt; &lt;!-- Dynamically assign the value of a complex expression --&gt; &lt; BlogPost : title = &quot; post.title + &#39; by &#39; + post.author.name &quot; /&gt; Passing Different Value Types ​ In the two examples above, we happen to pass string values, but any type of value can be passed to a prop. For example, given a post object: js export default { data () { return { post: { id: 1 , title: &#39;My Journey with Vue&#39; } } } } js const post = { id: 1 , title: &#39;My Journey with Vue&#39; } The following template: template &lt; BlogPost v-bind = &quot; post &quot; /&gt; Will be equivalent to: template &lt; BlogPost : id = &quot; post.id &quot; : title = &quot; post.title &quot; /&gt; Merge Behavior When Combining Bindings ​ When v-bind is used alongside explicit bindings on the same component, Vue internally calls mergeProps() to combine them. The merging strategy depends on the key type: Regular props — the last value wins: template &lt;!-- title === &#39;bar&#39; --&gt; &lt; BlogPost title = &quot;foo&quot; v-bind = &quot; { title: &#39;bar&#39; } &quot; /&gt; Event listeners — when passing listeners in a v-bind object, use the onEventName key convention . All handlers for the same event will be called (see v-on Listener Inheritance ): template &lt;!-- logs 1 and 2 --&gt; &lt; BlogPost @ click = &quot; console. log ( 1 ) &quot; v-bind = &quot; { onClick : () =&gt; console. log ( 2 ) } &quot; /&gt; class and style follow a similar merge strategy (see class and style Merging ). TIP The full merging rules are described in the mergeProps() API reference. One-Way Data Flow ​ All props form a one-way-down binding between the child property and the parent one: when the parent property updates, it will flow down to the child, but not the other way around. This prevents child components from accidentally mutating the parent&#39;s state, which can make your app&#39;s data flow harder to understand. In addition, every time the parent component is updated, all props in the child component will be refreshed with the latest value.

Planning the Migration | Scala 3 Migration Guide | Scala Documentation Scala 3 Migration Guide Planning the Migration Language Info: JavaScript is currently disabled, code tabs will still work, but preferences will not be remembered. This guide explains how to migrate a project from Scala 2.13 to Scala 3. Most Scala 2.13 code compiles with Scala 3, and the compiler rewrites much of the rest automatically. The main exception is Scala 2 macros, which have to be reimplemented (see Macro Libraries ). VirtusLab offers commercial support for Scala 3 migration, including up to 10 person-days of free Scala migration support . Choosing the Scala 3 Version Scala 3 has two long-term support (LTS) versions: Scala 3.3 uses the Scala 2.13 standard library and runs on JDK 8 or newer. It is maintained at least until September 2027. Scala 3.9 ships with the standard library compiled by Scala 3. It requires JDK 17 or newer (see JDK Compatibility ). For applications, we recommend using the latest Scala Next version, currently 3.10. Whichever version you target, migration usually goes from 2.13 to 3.3 first, then from 3.3 to later versions, even if the intermediate version is not put in production. Dependencies Between Scala 2.13 and Scala 3 Scala 2.13 and 3.3 support binary interoperability in both directions: Module compiled with Can use modules compiled with 2.13 2.13, and Scala 3 up to 3.7 (with -Ytasty-reader ) 3.3 2.13, and Scala 3 up to 3.3 3.9 2.13, and Scala 3 up to 3.9 This interoperability allows migrating projects gradually, as explained in the next section. There are however limitations: the Scala 3 compiler cannot expand Scala 2 macros, and the Scala 2.13 compiler does not support certain Scala 3 features. Migration Routes The best migration route for a project depends on its size, dependencies, and whether it uses Scala 2 macros. All at once: switch the entire build from 2.13 to Scala 3 in one change. This is the simplest route, and it suits small projects. Module by module, through 3.3: migrate one module at a time to Scala 3.3, in any order. The remaining 2.13 modules can depend on the migrated ones through the TASTy reader. Moving from 3.3 to 3.9 or 3.10 is a second, smaller migration. Top-down: migrate the applications first and the modules they depend on last. 2.13 modules never depend on migrated modules, so the migrated modules can be built with 3.9 or 3.10 right away. The 3.3 compiler is only used to apply source code rewrites. Cross-building: compile shared modules with both 2.13 and Scala 3 until all their users are migrated. This allows working around limitations of binary interoperability between Scala 2 and 3, and it keeps the 2.13 production build stable while working on the migration. Maintaining the two parallel builds creates overhead for the whole team, but it might be the best option for large projects. With -Xsource-features , Scala 2.13 adopts the Scala 3 behavior of changed features, such as implicit resolution and inferred override types, so that both builds behave the same (see Scala 2 with -Xsource:3 ). With the module-by-module and top-down routes, all modules keep using the _2.13 versions of their library dependencies until the migration is complete. If that is not possible, for example because of Scala 2 macros in these libraries, migrate all at once or use cross-building. The next page, Interoperability , explains this in more detail. Steps The rest of this guide follows the steps of the migration: Preparing on Scala 2.13 : changes to make before switching the compiler. Migrating to Scala 3.3 : the Scala 3.3 compiler rewrites the Scala 2.13 code, some fixes are done by hand. Migrating to Scala 3.9 and 3.10 : later compilers can apply further rewrites to the code. New features for Scaladoc | Scala Documentation &nbsp; New features for Scaladoc Language Info: JavaScript is currently disabled, code tabs will still work, but preferences will not be remembered. The new Scala version 3 comes with a completely new implementation of the documentation generator Scaladoc , rewritten from scratch. In this article you can find highlights of new features that are or will be introduced to Scaladoc. For general reference, visit Scaladoc manual . New features Markdown syntax The biggest change introduced in the new version of Scaladoc is the change of the default language for docstrings. So far Scaladoc only supported Wikidoc syntax. The new Scaladoc can still parse legacy Wikidoc syntax, however Markdown has been chosen as a primary language for formatting comments. To switch back to Wikidoc one can pass a global flag before running the doc task or one can define it for specific comments via the @syntax wiki directive. For more information on how to use the full power of docstings, check out Scaladoc docstrings Static site Scaladoc also provides an easy way for creating static sites for both documentation and blog posts in the similar way as Jekyll does. Thanks to this feature, you can store your documentation along-side with the generated Scaladoc API in a very convenient way. For more information on how to configure the generation of static sites check out Static documentation chapter Blog posts Blog posts are a specific type of static sites. In the Scaladoc manual you can find additional information about how to work with blog posts . Social links Furthermore, Scaladoc provides an easy way to configure your social media links e.g. Twitter or Discord. Experimental features The following features are currently (May 2021) not stable to be released with scaladoc, however we are happy to hear your feedback. Each feature has its own thread at scala-lang contributors site, where you can share your opinions. Snippet compiling One of the experimental features of Scaladoc is a compiler for snippets. This tool will allow you to compile snippets that you attach to your docstring to check that they actually behave as intended, e.g., to properly compile. This feature is very similar to the tut or mdoc tools, but will be shipped with Scaladoc out of the box for easy setup and integration into your project. Making snippets interactive—e.g., letting users edit and compile them in the browser—is under consideration, though this feature is not in scope at this time. Showcase: Hiding code Assert compilation errors Snippet includes For more information see Guides , or follow this Scala Contributors thread Type-based search Searching for functions by their symbolic names can be time-consuming. That is why the new scaladoc allows you to search for methods and fields by their types. So, for a declaration: extension [T](arr: IArray[T]) def span(p: T =&gt; Boolean): (IArray[T], IArray[T]) = ... Instead of searching for span we can also search for IArray[A] =&gt; (A =&gt; Boolean) =&gt; (IArray[A], IArray[A]) . To use this feature simply type the signature of the function you are looking for in the scaladoc searchbar. This is how it works: This feature is provided by the Inkuire search engine, which works for Scala 3 and Kotlin. To be up-to-date with the development of this feature, follow the Inkuire repository . For more information see Guides Note that this feature is still in development, so it can be subject to considerable change. If you encounter a bug or have an idea for improvement, don’t hesitate to create an issue on Inkuire or scala3 .

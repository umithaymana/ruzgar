Back in the halcyon days of jlox, I showed you this tricky example to explain the way super calls are dispatched: class A { method () { print &quot;A method&quot; ; } } class B &lt; A { method () { print &quot;B method&quot; ; } test () { super . method (); } } class C &lt; B {} C (). test (); Inside the body of the test() method, this is an instance of C. If super calls were resolved relative to the superclass of the receiver , then we would look in C&rsquo;s superclass, B. But super calls are resolved relative to the superclass of the surrounding class where the super call occurs . In this case, we are in B&rsquo;s test() method, so the superclass is A, and the program should print &ldquo;A method&rdquo;. This means that super calls are not resolved dynamically based on the runtime instance. The superclass used to look up the method is a static &mdash; practically lexical &mdash; property of where the call occurs. When we added inheritance to jlox, we took advantage of that static aspect by storing the superclass in the same Environment structure we used for all lexical scopes.

7. Security Configurations &mdash; BIND 9 9.21.29-dev documentation 7. Security Configurations View page source 7. Security Configurations  7.1. Threat Model  This section explains how to deploy BIND safely and evaluate potential vulnerabilities. It evolves with the attack landscape and our understanding. 7.1.1. Security Boundary  Unless stated otherwise below, network data is untrusted and subject to safety and correctness checks. No input, even malformed, should crash the server or significantly affect other conforming traffic. BIND 9 assumes only administrators can access: All files: zone, configuration, key, temporary, etc. Command-line arguments, environment, and standard input of BIND programs Authenticated controls connections statistics-channels Sockets used for update-policy type external Write access to response policy and catalog zone content Unauthorized access or misuse can cause arbitrary misbehavior and is not a basis for CVE assignment or security-sensitive handling. Client tools ( dig , delv , nsupdate , ...) are run by a user against servers of the user's choosing. Crashes (including assertion failures), hangs, and wrong output caused by malicious responses are ordinary bugs. 7.1.2. Non-Standard Behavior  The DNS protocol does not define some behavior, such as handling responses from non-conforming servers. BIND fills these gaps with its own safety checks and limits, subject to change as the protocol and deployments evolve. Unexpected behavior limited to zones on non-conforming servers, not affecting traffic to conforming servers and zones, is not a security issue in BIND . 7.1.3. Unsupported Features  Not a basis for CVE assignment or security-sensitive handling: Problems triggered only by resources (views, zones, ...) with classes other than Internet (IN), such as CHAOS (CH) or HESIOD (HS) Misbehavior of incorrectly implemented custom dlz , dyndb , or plugin modules Problems reproducible only in non-standard builds (sanitizers, developer mode) with no corresponding effect in a release build, e.g., a benign data race reported by TSAN Test code, sample and contrib modules Compile-time options not exposed by the build system Library code reachable only through calls BIND programs do not make 7.1.4. Authoritative Servers  primaries and UPDATE clients (within their authorization ) are partially trusted: they may break data they control and consume resources up to configured limits, but should not otherwise affect other conforming zones or crash the server. By protocol design, content of catalog zones affects the set of served zones, so their primaries and UPDATE clients are administrators (see Security Boundary ). Authoritative zone limits are intentionally lenient by default (unlimited size, long transfer timeouts, etc.). Resource exhaustion within configured limits is not a security issue. Set options in Server Resource Limits and Zone Transfers to fit the deployment, including zones where malicious clients may be authorized for Dynamic Update . Depending on configuration, NOTIFY and DS checks ( checkds , parental-agents ) can trigger outgoing queries, making the authoritative server act as a resolver. Resolver assumptions then apply. 7.1.5. Recursive Resolvers  Resolvers are inherently amplifiers: they legitimately send more traffic and do more work than the triggering client traffic. DNS specifications set no amplification limits, so BIND sets its own. Staying within max-query-count outgoing queries per client query is not a security issue. Other amplification is evaluated against Performance Impact baselines. Server Resource Limits limit damage from misbehaving authoritative servers. All these limits balance interoperability and attack protection, are subject to change as deployments evolve, and can temporarily break resolution of zones with excessively complex configurations or resolution paths. By protocol design, content of response policy zones can rewrite the answer to any query, so their primaries and UPDATE clients are administrators (see Security Boundary ). 7.1.6. Forwarding Resolvers  forwarders are trusted for their name subtree: they can make its names unresolvable, provide fake data, and see forwarded queries. 7.1.7. Data Integrity and Confidentiality  Zones not DNSSEC-secure ( RFC 4033 ) are spoofable, trivially by on-path attackers. Against off-path attackers, BIND applies only RFC 5452 measures, such as port and message ID

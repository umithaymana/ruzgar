Conflicts ​ The first variable declared in a rule head&#x27;s reference divides the reference in a leading constant portion and a trailing dynamic portion. Other rules are allowed to overlap with the dynamic portion (dynamic extent) without causing a compile-time conflict. package example # R1 p [ x ] . r := y if { x := &quot;q&quot; y := 1 } # R2 p . q . r := 2 Loading... In the above example, rule R2 overlaps with the dynamic portion of rule R1 &#x27;s reference ( [x].r ), which is allowed at compile-time, as these rules aren&#x27;t guaranteed to produce conflicting output. However, as R1 defines x as &quot;q&quot; and y as 1 , a conflict will be reported at evaluation-time. Conflicts are detected at compile-time, where possible, between rules even if they are within the dynamic extent of another rule. package example # R1 p [ x ] . r := y if { x := &quot;foo&quot; y := 1 } # R2 p . q . r := 2 # R3 p . q . r . s := 3 Loading... Above, R2 and R3 are within the dynamic extent of R1 , but are in conflict with each other, which is detected at compile-time (note the rego_type_error , rather than eval_conflict_error seen above). Rules are also not allowed to overlap with object values of other rules: package example # R1 p . q . r := { &quot;s&quot; : 1 } # R2 p [ x ] . r . t := 2 if { x := &quot;q&quot; } Loading... In the above example, R1 is within the dynamic extent of R2 and a conflict cannot be detected at compile-time. However, at evaluation-time R2 will attempt to inject a value under key t in an object value defined by R1 . This is a conflict, as rules are not allowed to modify or replace values defined by other rules. There is no conflict when the policy is updated to the following: package example # R1 p . q . r . s := 1 # R2 p [ x ] . r . t := 2 if { x := &quot;q&quot; } Loading... Functions may have an arbitrary number of inputs, but exactly one output. Function arguments may be any kind of term. For example, consider the following function: package functions foo ( [ x , { &quot;bar&quot; : y } ] ) := z if { z := { x : y } } The following calls would produce the logical mappings given: Call x y z := foo(a) a[0] a[1].bar z := foo([&quot;5&quot;, {&quot;bar&quot;: &quot;hello&quot;}]) &quot;5&quot; &quot;hello&quot; z := foo([&quot;5&quot;, {&quot;bar&quot;: [1, 2, 3, [&quot;foo&quot;, &quot;bar&quot;]]}]) &quot;5&quot; [1, 2, 3, [&quot;foo&quot;, &quot;bar&quot;]] If you need multiple outputs, write your functions so that the output is an array, object or set containing your results. If the output term is omitted, it is equivalent to having the output term be the literal true . Furthermore, if can be used to write shorter definitions. That is, the function declarations below are equivalent: package functions f ( x ) if { x == &quot;foo&quot; } f ( x ) if x == &quot;foo&quot; f ( x ) := true if { x == &quot;foo&quot; } f ( x ) := true if x == &quot;foo&quot; The outputs of user functions have some additional limitations, namely that they must resolve to a single value. If you write a function that has multiple possible bindings for an output variable, you will get a conflict error: package functions p ( x ) := y if { y := x [ _ ] } result := p ( [ 1 , 2 , 3 ] ) Loading... It is possible in Rego to define a function more than once, to achieve a conditional selection of which function to execute: Functions can be defined incrementally. package incremental q ( &quot;single&quot; , x ) := y if { y := x } q ( &quot;double&quot; , x ) := y if { y := x * 2 } package incremental result := q ( &quot;single&quot; , 2 ) Loading... package incremental result := q ( &quot;double&quot; , 2 ) Loading... A given function call will execute all functions that match the signature given. If a call matches multiple functions, they must produce the same output, or else a conflict error will occur: package incremental r ( 1 , x ) := y if { y := x } r ( x , 2 ) := y if { y := x * 4 } result := r ( 1 , 2 ) Loading... On the other hand, if a call matches no functions, then the result is undefined. package imcremental s ( x , 2 ) := y if { y := x * 4 } result := s ( 5 , 3 ) Loading... Function overloading ​ Rego does not support the overloading of functions by the number of parameters. If two function definitions are given with the same function name but different numbers of parameters, a compile-time type error is generated. package function_overloading_error r ( x ) := result if { result := 2 * x } r ( x , y ) := result if { result := 2 * x + 3 * y } Loading... In the unusual case that it is critical to use the same name, the function could be made to take the list of parameters as a single array. However, this approach is not generally recommended because it sacrifices some helpful compile-time checking and can be quite error-prone. package function_overloading_array r ( params ) := result if { count ( params ) == 1 result := 2 * params [ 0 ] } r ( params ) := result if { count ( params ) == 2 result := 2 * params [ 0 ] + 3 * params [ 1 ] } result := [ r ( [ 10 ] ) , r ( [ 10 , 1 ] ) ] Loading... Negation ​ important Users are recommended to use the future.keywords.not (or rego.v2 ) import whenever using the not keyword, as it fixes a long-standing semantic issue with negation in Rego. Read more about it in the Improved Negation Semantics section of the not keyword overview. To generate the content of a virtual document , OPA attempts to bind variables in the body of the rule such that all expressions in the rule evaluate to True. This generates the correct result when the expressions represent assertions about what states should exist in the data stored in OPA. In some cases, you want to express that certain states should not exist in the data stored in OPA. In these cases, negation must be used. For safety, a variable appearing in a negated expression must also appear in another non-negated equality expression in the rule. OPA will reorder expressions to ensure that negated expressions are evaluated after other non-negated expressions with the same variables. OPA will reject rules containing negated expressions that do not meet the safety criteria described above. The simplest use of negation involves only scalar values or variables and is equivalent to complementing the operator: package negation t if { greeting := &quot;hello&quot; not greeting == &quot;goodbye&quot; } Loading... Negation is required to check whether some value does not exist in a collection: not p[&quot;foo&quot;] . That is not the same as complementing the == operator in an expression p[_] == &quot;foo&quot; which yields p[_] != &quot;foo&quot; which means for any item in p , return true if the item is not &quot;foo&quot; . See more details in the Regal documentation .

Integrating OPA | Open Policy Agent Skip to main content The 2026 OPA Community Survey is open - We need your input On this page Integrating OPA OPA exposes domain-agnostic APIs that your service can call to manage and enforce policies. Read this page if you want to integrate an application, service, or tool with OPA. When integrating with OPA there are two interfaces to consider: Evaluation : OPA&#x27;s interface for asking for policy decisions. Integrating OPA is primarily focused on integrating an application, service, or tool with OPA&#x27;s policy evaluation interface. This integration results in policy decisions being decoupled from that application, service, or tool. Management : OPA&#x27;s interface for deploying policies, understanding status, uploading logs, and so on. This integration is typically the same across all OPA instances, regardless what software the evaluation interface is integrated with. Distributing policy, retrieving status, and storing logs in the same way across all OPA instances provides a unified management plane for policy across many different software systems. This page focuses predominantly on different ways to integrate with OPA&#x27;s policy evaluation interface and how they compare. For more information about the management interface: See the Bundle API for distributing policy and data to OPA. See the Status API for collecting status reports on bundle activation and agent health. See the Decision Log API for collecting a log of policy decisions made by agents. See the Health API for checking agent deployment readiness and health. See the Prometheus API endpoint to obtain insight into performance and errors. Evaluating Policies ​ OPA supports different ways to evaluate policies. The REST API returns decisions as JSON over HTTP. Also see the Language SDKs for working with the REST API in different languages. The Go API (GoDoc) returns decisions as simple Go types ( bool , string , map[string]any , etc.) WebAssembly compiles Rego policies into Wasm instructions so they can be embedded and evaluated by any WebAssembly runtime Custom compilers and evaluators may be written to parse evaluation plans in the low-level Intermediate Representation format, which can be emitted by the opa build command The SDK provides high-level APIs for obtaining the output of query evaluation as simple Go types ( bool , string , map[string]any , etc.) Integrating with the REST API ​ To integrate with OPA outside of Go, deploy OPA as a host-level daemon or sidecar container. Running OPA locally on the same host as your application or service helps ensure policy decisions are fast and highly-available. When your application or service needs to make policy decisions it can query OPA locally via HTTP. While it&#x27;s possible to call OPA&#x27;s REST API directly, you can also find a number of native language REST SDKs which make the integration easier. Named Policy Decisions ​ Use the Data API to query OPA for named policy decisions: POST /v1/data/&lt;path&gt; Content-Type : application/json { &quot;input&quot; : &lt;the input document&gt; } The &lt;path&gt; in the HTTP request identifies the policy decision to ask for. In OPA, every rule generates a policy decision. In the example below there are two decisions: example/authz/allow and example/authz/is_admin . package example . authz default allow := false allow if { input . method == &quot;GET&quot; input . path == [ &quot;salary&quot; , input . subject . user ] } allow if is_admin is_admin if &quot;admin&quot; in input . subject . groups You can request specific decisions by querying for &lt;package path&gt;/&lt;rule name&gt; . For example to request the allow decision execute the following HTTP request: POST /v1/data/example/authz/allow Content-Type : application/json { &quot;input&quot; : &lt;the input document&gt; } The body of the request specifies the value of the input document to use during policy evaluation. For example: POST /v1/data/example/authz/allow Content-Type : application/json { &quot;input&quot; : { &quot;method&quot; : &quot;GET&quot; , &quot;path&quot; : [ &quot;salary&quot; , &quot;bob&quot; ] , &quot;subject&quot; : { &quot;user&quot; : &quot;bob&quot; } } } OPA returns an HTTP 200 response code if the policy was evaluated successfully. Non-HTTP 200 response codes indicate configuration or runtime errors. The policy decision is contained in the &quot;result&quot; key of the response message body. For example, the above request returns the following response: 200 OK Content-Type : application/json { &quot;result&quot; : true } If the requested policy decision is undefined OPA returns an HTTP 200 response without the &quot;result&quot; key. For example, the following request for is_admin is undefined because there is no default value for is_admin and the input does not satisfy the is_admin rule body: POST /v1/data/example/authz/is_admin Content-Type : application/json { &quot;input&quot; : { &quot;subject&quot; : { &quot;user&quot; : &quot;bob&quot; , &quot;groups&quot; : [ &quot;sales&quot; , &quot;marketing&quot; ] } } } The response: 200 OK Content-Type : application/json { } For another example of how to integrate with OPA via HTTP see the HTTP API Authorization tutorial. Using the SDK client without a server ​ You might want to use the high-level SDK to load policy from the filesystem instead of a bundle server. This can be useful if you do not have a bundle server, or you ship policy with the application using the SDK. In that case, you can use the SDK as normal, but modify the configuration to use a file scheme and path, instead of a HTTP server resource path.

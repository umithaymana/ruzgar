Is there room for improvement? One way of doing that would be to use dynamic policy composition, where a single main policy acts as a &quot;router&quot;, and forwards queries to other packages based on attributes from the input. A natural attribute to use for CloudFormation templates might for example be the resource type, allowing policies to be grouped by the resource type they are meant to act on. See Dynamic Policy Composition for the pattern in general. Here is what such a main policy might look like: main.rego # METADATA # description: | # Dynamic routing to policy based in input.resource.type, # aggregating the deny rules found in all policies with a # matching package name # package system main := { &quot;allow&quot; : count ( violations ) == 0 , &quot;violations&quot; : violations , } # METADATA # description: | # Main routing logic, simply converting input.resource.type, e.g. # AWS::S3::Bucket to data.aws.s3.bucket and returning that document. # # By default, only input.action == &quot;CREATE&quot; | &quot;UPDATE&quot; will be routed # to the data.aws.s3.bucket document. If handling &quot;DELETE&quot; actions is # desirable, one may create a special policy for that by simply appending # &quot;delete&quot; to the package name, e.g. data.aws.s3.bucket.delete # route := document ( lower ( component ) , lower ( type ) ) if { [ &quot;AWS&quot; , component , type ] = split ( input . resource . type , &quot;::&quot; ) } violations contains msg if { # Aggregate all deny rules found in routed document some msg in route . deny } # # Basic input validation to avoid having to do this in each resource policy # violations contains &quot;Missing input.resource&quot; if { not input . resource } violations contains &quot;Missing input.resource.type&quot; if { not input . resource . type } violations contains &quot;Missing input.resource.id&quot; if { not input . resource . id } violations contains &quot;Missing input.action&quot; if { not input . action } # # Helpers # document ( component , type ) := data . aws [ component ] [ type ] if { input . action != &quot;DELETE&quot; } document ( component , type ) := data . aws [ component ] [ type ] . delete if { input . action == &quot;DELETE&quot; } The above policy will invoke the route rule to determine which package should be evaluated based on the input.resource.type , transforming a value such as AWS::S3::Bucket into a call to the data.aws.s3.bucket package, where each rule named deny will be evaluated, and the result aggregated into the final decision. Since most policies only deal with CREATE or UPDATE actions, it is better to avoid checking for this in all rules. Instead, the router appends .delete to the package name for DELETE operations, so that a request to delete e.g. an S3 bucket would invoke the data.aws.s3.bucket.delete package (if it exists). Additionally, some simple input validation is done at this stage, to avoid repeating it in each resource-specific policy. Modify the original policy to verify S3 bucket resources only: package aws . s3 . bucket deny contains sprintf ( &quot;S3 Bucket %s &#x27;AccessControl&#x27; attribute value must be &#x27;Private&#x27;&quot; , [ input . resource . id ] ) if { not bucket_is_private } bucket_is_private if { input . resource . properties . AccessControl == &quot;Private&quot; } Note that the bucket_create_or_update rule is no longer needed, as that is already asserted by the main policy. Quite an improvement in terms of readability, and a good foundation for further policy authoring. If you&#x27;d like to see more examples of policy utilizing this pattern, check out the policy directory in the OPA AWS CloudFormation Hook repo. OPA Authentication via AWS Secrets ​ OPA Configuration ​ Since the OPA server does not run inside the AWS Lambda, it is a good idea to require authentication to access its REST API, as described in the OPA documentation . A simple authz policy for checking the bearer token might look something like this: authz.rego package system . authz default allow := false allow if { input . identity == &quot;my_secret_token&quot; } Once created, remember to pass the appropriate flags to opa run to enable authentication / authorization: opa run --server --authentication=token --authorization=basic . OPA AWS CloudFormation Hook Configuration ​ If configured to use a bearer token for authenticating against OPA (by setting the OPA_AUTH_TOKEN_SECRET environment variable as described in the section on configuring the hook), the hook will try to fetch the token from the secret provided in the opaAuthTokenSecret (ARN) configuration attribute. Note that the token should be provided as a plain string in the secret (i.e. the SecretString ) and not wrapped in a JSON object. In order to fetch the token, the hook will need to be permitted to perform the secretsmanager:GetSecretValue operation. Note that the hook will only read the secret provided by opaAuthTokenSecret , but it&#x27;s recommended to limit the HookTypePolicy on the IAM role to the specific secret accessed, i.e. the same ARN provided in opaAuthTokenSecret . Example HookTypePolicy to allow the hook access to a specific secret: { &quot;Version&quot; : &quot;2012-10-17&quot; , &quot;Statement&quot; : [ { &quot;Sid&quot; : &quot;VisualEditor0&quot; , &quot;Effect&quot; : &quot;Allow&quot; , &quot;Action&quot; : &quot;secretsmanager:GetSecretValue&quot; , &quot;Resource&quot; : &quot;arn:aws:secretsmanager:eu-north-1:673240551671:secret:opa-cfn-token-l26bHK&quot; } ] } If you aren&#x27;t planning to use bearer tokens for authentication, you may remove the permission entirely.

GraphQL APIs | Open Policy Agent Skip to main content The 2026 OPA Community Survey is open - We need your input On this page GraphQL APIs GraphQL APIs have become a popular way for clients to query the information they require from a range of data sources. Generally, services providing a GraphQL API must authorize calls to control data access and mutations. OPA supports writing fine-grained, context-aware policies to implement GraphQL query authorization. In this tutorial, you&#x27;ll use a simple GraphQL server that accepts any GraphQL query that you issue, and echoes the OPA decision back as text. OPA will fetch policy bundles from a simple bundle server. OPA, the bundle server, and the GraphQL server will run as separate containers. For this tutorial, the following example scenario is used: Staff can see their own salaries ( query user($id: &lt;user&gt;) { salary } is permitted for &lt;user&gt; ) A manager can see their direct reports&#x27; salaries ( query user($id: &lt;user&gt;) { salary } is permitted for &lt;user&gt; &#x27;s manager) This tutorial requires Docker Compose to run a demo web server along with OPA. info Using GraphQL in Rego via the GraphQL built-in functions can involve some cumbersome code-sharing, for example when sharing custom @directive definitions between schemas used in different rules. Evaluate the range of available functions and review your GraphQL feature use to form a plan before embarking on major migrations. Steps ​ 1. Define the GraphQL schema ​ Most modern GraphQL frameworks encourage starting with a schema. Begin by defining the schema for this example. schema.gql type Employee { id : String ! salary : Int ! } schema { query : Query } type Query { employeeByID ( id : String ! ) : Employee } Every GraphQL service has a query type, and may or may not have a mutation type. These types are special because they define the entry points of every GraphQL query for the API covered by that schema. In the example above, exactly one query entry point is defined, the parameterized query employeeByID(id: String!) . 2. Create a policy bundle ​ GraphQL APIs allow surprising flexibility in how queries can be constructed, which makes writing policies for them a bit more challenging than for a REST API, which usually has a more fixed structure. To protect a particular endpoint or field, check whether they are referenced in the incoming GraphQL query. Using graphql.parse , an abstract syntax tree (AST) can be extracted from the incoming query, and then the tree can be walked to its leaves to see if the endpoint is the target of the query. Separate rules can then enforce conditions around the salary field, and who is allowed to access it. The policy below does all of the above in parts: Obtains the query AST (and validates it against the schema with graphql.parse ). Recursive traversal with walk() to obtain chunks of the AST with queries of interest present. Selection of nodes of interest by name and structure. Salary field selected. Every query of interest found has to pass one of the allowed_query rules, or the entire query is rejected.

A signed bundle is a normal opa bundle that includes a file named &quot;.signatures.json&quot;. For more information on signed bundles see openpolicyagent.org/docs/latest/management-bundles/#signing . The key to verify the signature of signed bundle can be provided using the --verification-key flag. For example, for RSA family of algorithms, the command expects a PEM file containing the public key. For HMAC family of algorithms (eg. HS256), the secret can be provided using the --verification-key flag. The --verification-key-id flag can be used to optionally specify a name for the key provided using the --verification-key flag. The --signing-alg flag can be used to specify the signing algorithm. The &#x27;run&#x27; command uses RS256 (by default) as the signing algorithm. The --scope flag can be used to specify the scope to use for bundle signature verification. Example: $ opa run --verification-key secret --signing-alg HS256 --bundle bundle.tar.gz The &#x27;run&#x27; command will read the bundle &quot;bundle.tar.gz&quot;, check the &quot;.signatures.json&quot; file and perform verification using the provided key. An error will be generated if &quot;bundle.tar.gz&quot; does not contain a &quot;.signatures.json&quot; file. For more information on the bundle verification process see openpolicyagent.org/docs/latest/management-bundles/#signature-verification . The &#x27;run&#x27; command can ONLY be used with the --bundle flag to verify signatures for existing bundle files or directories following the bundle structure. To skip bundle verification, use the --skip-verify flag. The --watch flag can be used to monitor policy and data file-system changes. When a change is detected, the updated policy and data is reloaded into OPA. Watching individual files (rather than directories) is generally not recommended as some updates might cause them to be dropped by OPA. OPA will automatically perform type checking based on a schema inferred from known input documents and report any errors resulting from the schema check. Currently this check is performed on OPA&#x27;s Authorization Policy Input document and will be expanded in the future. To disable this, use the --skip-known-schema-check flag. The --v0-compatible flag can be used to opt-in to OPA features and behaviors that were the default in OPA v0.x. Behaviors enabled by this flag include: setting OPA&#x27;s listening address to &quot;:8181&quot; by default, corresponding to listening on every network interface. expecting v0 Rego syntax in policy modules instead of the default v1 Rego syntax. The &#x27;sign&#x27; command generates a digital signature for policy bundles. It generates a &quot;.signatures.json&quot; file that dictates which files should be included in the bundle, what their SHA hashes are, and is cryptographically secure. The signatures file is a JSON file with an array containing a single JSON Web Token (JWT) that encapsulates the signature for the bundle. The --signing-alg flag can be used to specify the algorithm to sign the token. The &#x27;sign&#x27; command uses RS256 (by default) as the signing algorithm. See openpolicyagent.org/docs/latest/configuration/#keys for a list of supported signing algorithms. The key to be used for signing the JWT MUST be provided using the --signing-key flag. For example, for RSA family of algorithms, the command expects a PEM file containing the private key. For HMAC family of algorithms (e.g. HS256), the secret can be provided using the --signing-key flag. opa &#x27;sign&#x27; can ONLY be used with the --bundle flag to load paths that refer to existing bundle files or directories following the bundle structure. $ opa sign --signing-key /path/to/private_key.pem --bundle foo Where foo has the following structure: foo/ | +-- bar/ | | | +-- data.json | +-- policy.rego | +-- .manifest This will create a &quot;.signatures.json&quot; file in the current directory.

XSS Defense Philosophy &para; XSS happens when an application puts untrusted data into a page in a way that lets the browser treat it as code. For example, a user's comment that should appear as plain text instead runs as JavaScript or adds HTML the attacker controls. Untrusted data is anything your application did not create itself, such as form input, URL parameters, data stored by users, and responses from other services. To prevent XSS, every place where untrusted data is added to the page needs protection. Coverage is what matters: an application that protects 99 places and misses one is still vulnerable. Many frameworks escape every value they render by default, whether it is trusted or not. We recommend this approach, because it does not depend on deciding correctly which data is untrusted. The appropriate protection depends on how the data is used. Prefer safe APIs that treat data as text. When inserting data into a context that interprets syntax, use the appropriate context-specific output encoding. When an application needs to accept user-authored HTML, use a maintained HTML sanitizer. Input validation can enforce expected formats, but it does not replace these protections. Framework security features help prevent XSS, but unsafe APIs and framework bypasses can reintroduce vulnerabilities. Output Encoding &para; When you need to safely display data exactly as a user types it in, output encoding is recommended. Variables should not be interpreted as code instead of text. This section covers each form of output encoding, where to use it, and when you should not use dynamic variables at all. First, when you wish to display data as the user typed it in, start with your framework’s default output encoding protection. Automatic encoding and escaping functions are built into most frameworks. If you’re not using a framework or need to cover gaps in the framework then you should use an output encoding library. Each variable used in the user interface should be passed through an output encoding function. A list of output encoding libraries is included in the appendix. There are many different output encoding methods because browsers parse HTML, JS, URLs, and CSS differently. Using the wrong encoding method may introduce weaknesses or harm the functionality of your application. This creates a text node without parsing HTML; it does not HTML-encode the value. Pass the original text without pre-encoding it. Do not use it for untrusted script or style content; HTMLScriptElement.textContent sets executable code. &amp; &amp;amp; &lt; &amp;lt; &gt; &amp;gt; " &amp;quot; ' &amp;#x27; Output Encoding for “HTML Attribute Contexts” &para; Use HTML attribute encoding for data inserted into ordinary text attributes, such as title or value . Keep element and attribute names fixed. Attributes containing URLs, CSS, HTML, or JavaScript need controls for those additional contexts. The placeholder below represents data already encoded for a quoted HTML attribute: &lt; input value = "ENCODED DATA" &gt; Always surround attribute values with double ( " ) or single ( ' ) quotation marks. Use your framework's or library's attribute encoder to protect the surrounding quotes and other HTML syntax. Spaces do not end a quoted value, so encoding every space or every non-alphanumeric character is unnecessary. The HTML parsing rules distinguish quoted values from unquoted ones, where whitespace ends the value. HTML attribute encoding alone does not protect JavaScript in an event-handler attribute: the HTML parser decodes character references before the JavaScript is interpreted. Encoding more characters as HTML entities does not remove that second context. Prefer addEventListener() with trusted handler functions and pass user values as data. For unavoidable legacy templates, follow the library's documented JavaScript-in-HTML context for data inside a quoted JavaScript string within a quoted HTML attribute; an encoder cannot make untrusted handler code safe. When updating an existing element from JavaScript, element.setAttribute("title", value) assigns the value directly; it does not HTML-encode it. Do not pre-encode a runtime value for this ordinary text attribute. Keep the attribute name fixed and safe: event-handler attributes and srcdoc can interpret their values as code or HTML . Output Encoding for “JavaScript Contexts” &para; When a server template inserts string data into an inline script, use an encoder documented for both the JavaScript string and the enclosing HTML script. The placeholder below represents data already encoded for that location; the template supplies the quotes: &lt; script &gt; const message = "ENCODED DATA" ;&lt;/ script &gt; Do not insert untrusted code, identifiers, or expressions. Use a maintained encoder and follow its context contract instead of escaping quotes manually or applying a generic \xHH rule. The OWASP Java Encoder context guide distinguishes script blocks, quoted event-handler strings, and standalone JavaScript. Support for ordinary template literals depends on the library and version; it does not imply support for tagged templates or ${...} expression bodies. These encoders protect string placement, not subsequent use: passing the resulting value to eval() or another code-interpreting sink remains unsafe. For JSON, verify that the Content-Type header is application/json and not text/html to prevent XSS. Output Encoding for “CSS Contexts” &para; “CSS Contexts” refer to data inserted into CSS, such as inline styles or style sheets. Do not interpolate untrusted data directly into CSS source, including selectors, property names, or declaration blocks. Placing data inside a CSS property value does not by itself make arbitrary input safe, because the input may alter the intended CSS syntax. &lt; style &gt; selector { property : $ varUnsafe ; } &lt;/ style &gt; &lt; style &gt; selector { property : "$varUnsafe" ; } &lt;/ style &gt; &lt; span style = "property : $varUnsafe" &gt; Oh no &lt;/ span &gt; When dynamic styling is needed, use a CSSOM API such as element.style.setProperty() with a fixed property name and a value constrained by an allowlist specific to that property. The API sets a CSS property value, but does not validate whether that value is appropriate for your application's security requirements. Properties that can load resources, such as background-image , require separate URL validation against the schemes and destinations your application permits. Output Encoding for “URL Contexts” &para; “URL Contexts” refer to variables placed into a URL. Most commonly, a developer will add a parameter or URL fragment to a URL base that is then displayed or used in some operation. Use URL Encoding for these scenarios. &lt; a href = "http://www.owasp.org?test=$varUnsafe" &gt; link &lt;/ a &gt; Encode all characters with the %HH encoding format. Make sure any attributes are fully quoted, same as JS and CSS. Common Mistake &para; There will be situations where you use a URL in different contexts. The most common one would be adding it to an href or src attribute of an &lt;a&gt; tag. In these scenarios, you should do URL encoding, followed by HTML attribute encoding. url = "https://site.com?data=" + urlencode(parameter) &lt; a href = 'attributeEncode(url)' &gt; link &lt;/ a &gt; When using JavaScript to construct a URL, use encodeURIComponent() to encode each untrusted query parameter value. It encodes a URL component; it does not validate a complete URL. Base64url represents bytes using a URL-safe alphabet. Protocols such as JSON Web Tokens (JWTs) use an unpadded form that encodeURIComponent() leaves unchanged. Use base64url only when the receiver expects it. After decoding, apply the output encoding or sanitization required by the destination context. Dangerous Contexts &para; Output encoding is not perfect. It will not always prevent XSS. These locations are known as dangerous contexts . Dangerous contexts include: &lt; script &gt; Directly in a script &lt;/ script &gt; &lt;!-- Inside an HTML comment --&gt; &lt; style &gt; Directly in CSS &lt;/ style &gt; &lt; div ToDefineAnAttribute = test /&gt; &lt; ToDefineATag href = "/test" /&gt; Other areas to be careful with include: Callback functions Where URLs are handled in code such as this CSS { background-url : “javascript:alert(xss)”; } Untrusted JavaScript event-handler code (for example, an entire onclick value). Prefer trusted functions registered with addEventListener() ; see the HTML Attribute Contexts section for legacy string interpolation. Unsafe JS functions like eval() , setInterval() , setTimeout() Don't place variables into dangerous contexts as even with output encoding, it will not prevent an XSS attack fully. HTML Sanitization &para; When users need to author HTML, developers may let users change the styling or structure of content inside a WYSIWYG editor. Output encoding in this case will prevent XSS, but it will break the intended functionality of the application. The styling will not be rendered. In these cases, HTML Sanitization should be used. HTML Sanitization will strip dangerous HTML from a variable and return a safe string of HTML. OWASP recommends DOMPurify for HTML Sanitization. let clean = DOMPurify . sanitize ( dirty ); There are some further things to consider: If you sanitize content and then modify it afterwards, you can easily void your security efforts. If you sanitize content and then send it to a library for use, check that it doesn’t mutate that string somehow. Otherwise, again, your security efforts are void. You must regularly patch DOMPurify or other HTML Sanitization libraries that you use. Browsers change functionality and bypasses are being discovered regularly. Safe Sinks &para; Security professionals often talk in terms of sources and sinks. If you pollute a river, it'll flow downstream somewhere. It’s the same with computer security. XSS sinks are places where variables are placed into your webpage. Thankfully, many sinks where variables can be placed are safe. This is because these sinks treat the variable as text and will never execute it.

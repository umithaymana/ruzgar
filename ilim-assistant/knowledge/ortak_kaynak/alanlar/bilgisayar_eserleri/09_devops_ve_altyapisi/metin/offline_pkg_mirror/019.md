If you have a new installation it comes by default, otherwise you need to add the following props to your config file middlewares : audit : enabled : true # timeout: 10000 Package Filter ​ Since: verdaccio@6.4.0 Verdaccio ships with a bundled, optional filter plugin @verdaccio/package-filter that controls which package versions are visible to consumers by filtering manifest responses. info It is disabled by default. To enable it, add it under filters in config.yaml (with no rules it is a no-op): filters : &#x27;@verdaccio/package - filter&#x27; : Supported options: minAgeDays : hide versions published less than N days ago (quarantine window). dateThreshold : only serve versions published before a given date (e.g. &#x27;2024-01-01&#x27; ). When combined with minAgeDays , the earlier cutoff wins. block : list of rules to hide versions. Each rule can target a scope , a package name, or a package + versions semver range. Add strategy: replace to substitute a blocked version with the nearest older safe one (useful for transitive deps). allow : same shape as block , but exempts the matching scope/package/versions from all rules (including minAgeDays and dateThreshold ). allow takes precedence over block . Example combining all options: filters : &#x27;@verdaccio/package-filter&#x27; : minAgeDays : 7 dateThreshold : &#x27;2025-01-01&#x27; block : - scope : &#x27;@malicious&#x27; - package : &#x27;typosquat-pkg&#x27; - package : &#x27;compromised-lib&#x27; versions : &#x27;&gt;=3.0.0&#x27; - package : &#x27;legacy-lib&#x27; versions : &#x27;&gt;=2.0.0&#x27; strategy : replace allow : - scope : &#x27;@my-org&#x27; - package : &#x27;compromised-lib&#x27; versions : &#x27;3.0.1&#x27; See the plugin README for manifest cleanup behavior and debug namespaces. Feature Flags (former Experiments) ​ Verdaccio includes a flags configuration setting (formerly named experiments ) that can be placed in the config.yaml and is completely optional. This allows shipping new things without affecting production environments. We can add new features and get feedback from the community who decides to use them. Every flag is experimental Everything under flags is an experiment, including the flags that have existed for several releases. A flag, the endpoints it registers or its behaviour may change in a future release, in any line, depending on the feedback we receive. Do not depend on a flag in production unless you are prepared to follow those changes. By default, all flags are off (false). Examples: flags : changePassword : false webLogin : true The flags currently available are: Flag Lines What it enables changePassword 6.x, 7.x changing a password from the web UI createUser 6.x, 7.x user registration from the web UI webLogin 6.x, 7.x browser-based login for the CLI stage 7.x staged publishing ( npm stage ) tfa 7.x two-factor authentication tarballMetadata 7.x per-version READMEs and dist stats from tarballs stage , tfa and tarballMetadata are not available in 6.x , which does not receive new features. searchRemote does nothing You may find a searchRemote flag in old configuration files and in the 6.x type definitions. It is inert : 6.x overrides it to false before anything reads it, and no code consumes it. Searching the uplinks is not gated by it on either line. It is gone from 7.x. Remove it from your config; keeping it only produces a startup warning about enabled experiments. To disable console warnings related to the flags or experiments, you must comment out the complete flags and experiments sections.

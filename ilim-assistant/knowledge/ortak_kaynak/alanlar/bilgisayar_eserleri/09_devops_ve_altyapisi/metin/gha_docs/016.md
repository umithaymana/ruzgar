Copy markdown Understanding the risk of script injections When creating workflows, custom actions , and composite actions , you should always consider whether your code might execute untrusted input from attackers. This can occur when an attacker adds malicious commands and scripts to a context. When your workflow runs, those strings might be interpreted as code which is then executed on the runner. Attackers can add their own malicious content to the github context , which should be treated as potentially untrusted input. These contexts typically end with body , default_branch , email , head_ref , label , message , name , page_name , ref , and title . For example: github.event.issue.title , or github.event.pull_request.body . You should ensure that these values do not flow directly into workflows, actions, API calls, or anywhere else where they could be interpreted as executable code. By adopting the same defensive programming posture you would use for any other privileged application code, you can help security harden your use of GitHub Actions. For information on some of the steps an attacker could take, see Secure use reference . In addition, there are other less obvious sources of potentially untrusted input, such as branch names and email addresses, which can be quite flexible in terms of their permitted content. For example, zzz&quot;;echo${IFS}&quot;hello&quot;;# would be a valid branch name and would be a possible attack vector for a target repository. The following sections explain how you can help mitigate the risk of script injection. Example of a script injection attack A script injection attack can occur directly within a workflow&#x27;s inline script. In the following example, an action uses an expression to test the validity of a pull request title, but also adds the risk of script injection: - name: Check PR title run: | title=&quot;${{ github.event.pull_request.title }}&quot; if [[ $title =~ ^octocat ]]; then echo &quot;PR title starts with &#x27;octocat&#x27;&quot; exit 0 else echo &quot;PR title did not start with &#x27;octocat&#x27;&quot; exit 1 fi This example is vulnerable to script injection because the run command executes within a temporary shell script on the runner. Before the shell script is run, the expressions inside ${{ }} are evaluated and then substituted with the resulting values, which can make it vulnerable to shell command injection. To inject commands into this workflow, the attacker could create a pull request with a title of a&quot;; ls $GITHUB_WORKSPACE&quot; : In this example, the &quot; character is used to interrupt the title=&quot;${{ github.event.pull_request.title }}&quot; statement, allowing the ls command to be executed on the runner. You can see the output of the ls command in the log: Run title=&quot;a&quot;; ls $GITHUB_WORKSPACE&quot;&quot; README.md code.yml example.js For best practices keeping runners secure, see Secure use reference . Workflow dependency lockfiles - GitHub Docs Skip to main content Skip to content Search or ask Copilot / Menu Collapse sidebar Expand sidebar In this article Workflow dependency lockfiles A lockfile pins every action your workflows depend on to a verified commit, so the code you reviewed is the code that runs. Copy markdown In this article Why lock workflow dependencies? Workflows often reference an action by a tag or branch, such as uses: octo-org/deploy-action@v3 or uses: octo-org/deploy-action@main . GitHub Actions resolves that reference to whatever commit the tag or branch points to at run time. Tags and branches can move. As a result, the code that runs is not guaranteed to be the code that the workflow author originally reviewed. If an upstream maintainer&#x27;s account is compromised and a tag is repointed, your repositories could run malicious code. A workflow dependency lockfile pins a commit SHA to every action your workflows depend on, including transitive dependencies. It doesn&#x27;t pin calls to reusable workflows ( jobs.&lt;job_id&gt;.uses ). To pin a reusable workflow, reference it by its full commit SHA. A lockfile controls which action code runs on the runner. It doesn&#x27;t control other build inputs, such as input parameters, secrets, or the runner image. A lockfile gives you the following for the action code it covers: Reproducible resolution of action dependencies Reviewable dependency changes and Dependabot version updates An auditable inventory of your CI/CD systems&#x27; action dependencies How does the lockfile work? The lockfile is defined in a repository at .github/workflows/actions.lock . It&#x27;s generated by gh actions-lock , a GitHub CLI extension, and should never be edited by hand. You can onboard a repository&#x27;s workflows to the lockfile one at a time or all at once. After a workflow is onboarded: Every action dependency the workflow uses must be present in the lockfile. The locked commit is what runs when the workflow executes, and what allowed actions policies check. This commit must be reachable from the branch or tag recorded for it in the lockfile, in the action&#x27;s own repository. A commit that exists only in a fork, or that&#x27;s no longer reachable from that branch or tag, is rejected when the workflow runs. A lockfile covers the workflows in its own repository, including transitive dependencies (actions that your action dependencies use), except for dependencies of reusable workflow calls. Reusable workflows can have their own lockfiles too. A reusable workflow&#x27;s dependencies are covered by the lockfile of the repository where it&#x27;s defined, not by the lockfile of the repository that calls it. What does the lockfile record? The lockfile has two sections. workflows records which dependencies each onboarded workflow uses, and dependencies records which commit each of those references resolves to. # This file is machine-generated by `gh actions-lock`. # Do not edit by hand; run `gh actions-lock` to update. # Docs: https://gh.io/actions-lockfile version: &#x27;v0.0.3&#x27; workflows: &#x27;.github/workflows/ci.yml&#x27; : - &#x27;octo-org/deploy-action@v3.1.0&#x27; dependencies: &#x27;octo-org/deploy-action@v3.1.0&#x27;: ref: &#x27;v3.1.0&#x27; commit: &#x27;sha1-...&#x27; owner_id: 44036562 repo_id: 197814629 Each dependency records: ref : The tag or branch the commit was resolved from. commit : The exact commit the reference resolved to. This is the code that will run. owner_id and repo_id : The numeric identity of the source repository. GitHub Actions uses these to confirm at run time that the repository behind the name is still the one you locked. This structured format gives tools like Dependabot a machine-readable record they can use to manage dependency updates, without relying on YAML comments as version annotations. How do lockfiles compare with SHA pinning? GitHub has historically recommended pinning third-party actions to a full-length commit SHA in your workflow files. For repositories that adopt a lockfile, SHA pinning within workflow files is no longer necessary . The lockfile is the better option because it: Supports transitive dependencies Makes workflow files easier to read Records the identity of the source repository A lockfile also satisfies the separate Require actions to be pinned to a full-length commit SHA policy for workflows that are onboarded to it.

Each range-vector window counts its underlying samples, including samples consumed inside subqueries. Materialized subquery results are not counted again, while overlapping windows can count the same underlying sample repeatedly. totalQueryableSamplesPerStep : (Only with stats=all and when per-step stats are enabled.) Per-step underlying sample consumption; same semantics as totalQueryableSamples for the equivalent instant query. samplesRead : Samples read by the evaluator, counting only new points when range-vector windows overlap. With query-cost enabled, this includes all subquery reads, even for child steps in gaps between the consumed parent windows. Without it, subquery reads are attributed only to consumed windows. This measures evaluator input rather than physical storage I/O. samplesReadPerStep : (Only with stats=all and when per-step stats are enabled.) Per-step count of samples read (delta semantics for range-vector). seriesTouched : Number of series consumed during execution, summed across selectors. Repeated selectors can count the same series more than once. This allows comparison with the query cost estimate without requesting a second estimation through cost=true . peakSamples : Peak number of samples in memory during evaluation. Floats count as one sample; native histograms are weighted by their in-memory size. Fixed @ subqueries read their window once, charging reads to the first parent step, while each parent step counts its logical underlying consumption. The server also exposes two Prometheus metrics: prometheus_engine_query_samples_total (logical underlying sample consumption) and prometheus_engine_query_samples_read_total (samples read). See Per-step stats for the promql-per-step-stats feature flag. When the query-cost feature flag is enabled, the instant and range query endpoints accept a cost=&lt;bool&gt; parameter. It is a plain on/off switch, not a set of levels: cost=true enables the comparison, and any value that does not parse as a boolean is rejected with HTTP 400 ( bad_data ). When cost is true , the response data includes an additional cost object comparing estimated storage input with the actual cost measured during execution: &quot;cost&quot; : { &quot;estimated&quot; : { &quot;seriesTouched&quot; : 42 , &quot;samplesRead&quot; : 5040 }, &quot;actual&quot; : { &quot;seriesTouched&quot; : 40 , &quot;samplesRead&quot; : 4980 , &quot;peakSamples&quot; : 320 } } The estimated seriesTouched and samplesRead values are approximations that can be higher or lower than actual cost: see Query cost for how they are computed and their accuracy limitations. peakSamples is reported only for the actual cost; there is no estimated peakSamples . The comparison is informational: the estimate is never used to reject a query. Note that requesting cost=true adds some overhead: Prometheus performs an additional cost estimation after building the query and before executing it, including index enumeration and bounded sampling of chunk data. This estimation reserves a query concurrency slot and counts against the query&#x27;s duration limit, which starts when the query is built, including a shorter max_query_duration , and against a request timeout : if either expires or the client cancels during estimation, the query fails with the usual timeout or cancellation error. If estimation fails for any other reason, the query still runs, and its result is returned with a warning and without a cost comparison. Query cost The query cost endpoints require the query-cost feature flag. The following endpoints estimate the resource cost of a query without executing it , allowing clients to gauge how expensive a query would be before running it: GET /api/v1/query_cost POST /api/v1/query_cost GET /api/v1/query_range_cost POST /api/v1/query_range_cost /api/v1/query_cost accepts the same URL query parameters as /api/v1/query , and /api/v1/query_range_cost accepts the same parameters as /api/v1/query_range , so a request accepted by one endpoint is accepted by the other. The parameters that only shape the response of an executed query ( limit , stats and cost ) are validated in the same way and then ignored, since these endpoints return no query result. As with the other query endpoints, parameters may be URL-encoded in the request body using the POST method with a Content-Type: application/x-www-form-urlencoded header. The data section of the response has the following format: { &quot;estimate&quot; : { &quot;seriesTouched&quot; : &lt;number&gt; , &quot;samplesRead&quot; : &lt;number&gt; } } seriesTouched : the number of series the query reads, summed per selector. samplesRead : an estimate of the samplesRead query statistic , the samples the evaluator reads in the engine&#x27;s sample units, rather than the peak number of samples in memory. Estimation enumerates matching series in the index and, when supported by storage, samples chunk data to measure sample density and native histogram size. The number of chunk samples is bounded, but index enumeration still scales with selector cardinality and the number of storage blocks. Samples are expressed in the engine&#x27;s sample units: a float counts as one unit, while native histograms are weighted by their in-memory size. Estimates include the extra lookback window consumed by anchored and smoothed selectors. Anchored range selectors extend their window by one lookback delta; smoothed range selectors extend it by two. Smoothed instant selectors also read a window spanning two lookback deltas. Density sampling examines up to 50 chunks in each selector&#x27;s actual time window. For fully sampled series, the observed sample counts constrain range-selector estimates so that gaps and short-lived series do not imply continuous scraping. A series cut short by the sampling budget contributes only its measured sample interval, including gaps between chunks. Histogram sizing samples up to 50 series and may use a shorter window near the selector&#x27;s end. These samples may not represent the full population, especially when series have different densities or histogram sizes. Density sampling follows storage iteration order and can favor earlier series or earlier portions of a long query window. Both values may overestimate or underestimate actual cost. Shared selectors can count the same series repeatedly, indexed series can lack samples in the query window, and sampled density and histogram sizes may not represent all matching series. info() produces an incomplete-estimate warning because its additional runtime-dependent selections are omitted; its second argument is a label filter, not an independent selector. When remote read is configured, series enumeration also queries the remote read endpoints, and density sampling is unavailable. Estimates then assume the global scrape_interval and float-sized samples, with a warning for each selector that matches series. Estimation occupies one of the --query.max-concurrency slots for its duration. The deadline also applies while waiting for a slot. It uses query_max_duration when configured and otherwise --query.timeout , unless the request sets a shorter timeout or max_query_duration .

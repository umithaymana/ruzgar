Cost estimation is unavailable in agent mode. When the query-cost feature flag is enabled, the engine also enforces the reloadable cost limits configured under the global: section of the configuration file ( query_max_series , query_max_samples_read , and query_max_duration ). These limits are enforced during query execution against the query&#x27;s actual running cost, not against the estimate above. A query is rejected as soon as the number of series it loads or the number of samples it reads exceeds the configured limit, and query_max_duration surfaces as a query timeout. The estimate returned by these endpoints is informational only and is never used to reject a query. These limits apply to every query the engine evaluates, not only to API requests. Recording and alerting rules are subject to them too: a rule whose query exceeds a limit fails to evaluate like any other query error, and query_max_duration replaces --query.timeout as the timeout of rule queries. With query-cost enabled, sample accounting includes all storage input consumed by child evaluators, even when their output falls between outer query windows. Reusing a materialized child result does not charge its storage reads again. A client may lower any of these ceilings for a single request with the max_series , max_samples_read and max_query_duration parameters. These can only tighten the operator-set value, never loosen it: a request asking for a value above the ceiling is rejected with HTTP 400 ( bad_data ) so that the caller sees that the limit it asked for was not applied, instead of being silently clamped down. The timeout parameter can also shorten the deadline, but a larger value is capped at the effective duration ceiling rather than rejected. A query rejected by the series or samples-read limit during execution returns HTTP 422 with the errorType cost_limit , distinguishing a cost rejection from other execution failures. A query stopped by the duration limit usually fails like any other query timeout, with HTTP 503 and the errorType timeout . If the limit expires while the query is still loading series from storage, local or remote, the query can instead fail with HTTP 422 and the errorType execution ( expanding series: context deadline exceeded ), and is not counted under max_duration below. The engine also exposes three metrics while the feature flag is enabled: prometheus_engine_query_rejected_total (rejections by reason ), prometheus_engine_query_series_touched and prometheus_engine_query_samples_read (per-query distributions). The reason is max_series , max_samples_read or max_duration . max_duration counts queries stopped by query_max_duration or max_query_duration ; expiries of --query.timeout or a request timeout are not counted. Formatting query expressions The following endpoint formats a PromQL expression in a prettified way: GET /api/v1/format_query POST /api/v1/format_query URL query parameters: query=&lt;string&gt; : Prometheus expression query string. You can URL-encode these parameters directly in the request body by using the POST method and Content-Type: application/x-www-form-urlencoded header. This is useful when specifying a large query that may breach server-side URL character limits. The data section of the query result is a string containing the formatted query expression. Note that any comments are removed in the formatted string. GET /api/v1/series POST /api/v1/series URL query parameters: match[]=&lt;series_selector&gt; : Repeated series selector argument that selects the series to return. Optional. 0 means disabled. You can URL-encode these parameters directly in the request body by using the POST method and Content-Type: application/x-www-form-urlencoded header. This is useful when specifying a large or dynamic number of series selectors that may breach server-side URL character limits. Note that the start and end times are approximate and the result may contain label values for series which have no samples in the given interval.

Notification template examples | Prometheus Prometheus Docs Download Community Support &amp; Training Blog Ctrl + K Show nav Notification template examples The following are all different examples of alerts and corresponding Alertmanager configuration file setups (alertmanager.yml). Each use the Go templating system. Customizing Slack notifications In this example we&#x27;ve customised our Slack notification to send a URL to our organisation&#x27;s wiki on how to deal with the particular alert that&#x27;s been sent. global: # Also possible to place this URL in a file. # Ex: `slack_api_url_file: &#x27;/etc/alertmanager/slack_url&#x27;` slack_api_url: &#x27;&lt;slack_webhook_url&gt;&#x27; route: receiver: &#x27;slack-notifications&#x27; group_by: [alertname, datacenter, app] receivers: - name: &#x27;slack-notifications&#x27; slack_configs: - channel: &#x27;#alerts&#x27; text: &#x27;https://internal.myorg.net/wiki/alerts/{{ .GroupLabels.app }}/{{ .GroupLabels.alertname }}&#x27; Accessing annotations in CommonAnnotations In this example we again customize the text sent to our Slack receiver accessing the summary and description stored in the CommonAnnotations of the data sent by the Alertmanager. Alert groups: - name: Instances rules: - alert: InstanceDown expr: up == 0 for: 5m labels: severity: page # Prometheus templates apply here in the annotation and label fields of the alert. annotations: description: &#x27;{{ $labels.instance }} of job {{ $labels.job }} has been down for more than 5 minutes.&#x27; summary: &#x27;Instance {{ $labels.instance }} down&#x27; Receiver - name: &#x27;team-x&#x27; slack_configs: - channel: &#x27;#alerts&#x27; # Alertmanager templates apply here. text: &quot;&lt;!channel&gt; \nsummary: {{ .CommonAnnotations.summary }}\ndescription: {{ .CommonAnnotations.description }}&quot; Ranging over all received Alerts Finally, assuming the same alert as the previous example, we customize our receiver to range over all of the alerts received from the Alertmanager, printing their respective annotation summaries and descriptions on new lines. Receiver - name: &#x27;default-receiver&#x27; slack_configs: - channel: &#x27;#alerts&#x27; title: &quot;{{ range .Alerts }}{{ .Annotations.summary }}\n{{ end }}&quot; text: &quot;{{ range .Alerts }}{{ .Annotations.description }}\n{{ end }}&quot; Defining reusable templates Going back to our first example, we can also provide a file containing named templates which are then loaded by Alertmanager in order to avoid complex templates that span many lines. Create a file under /alertmanager/template/myorg.tmpl and create a template in it named &quot;slack.myorg.text&quot;: {{ define &quot;slack.myorg.text&quot; }}https://internal.myorg.net/wiki/alerts/{{ .GroupLabels.app }}/{{ .GroupLabels.alertname }}{{ end}} The configuration now loads the template with the given name for the &quot;text&quot; field and we provide a path to our custom template file: global: slack_api_url: &#x27;&lt;slack_webhook_url&gt;&#x27; route: receiver: &#x27;slack-notifications&#x27; group_by: [alertname, datacenter, app] receivers: - name: &#x27;slack-notifications&#x27; slack_configs: - channel: &#x27;#alerts&#x27; text: &#x27;{{ template &quot;slack.myorg.text&quot; . }}&#x27; templates: - &#x27;/etc/alertmanager/templates/myorg.tmpl&#x27; This example is explained in further detail in this blogpost . Defining a reusable HTML email template The HTML body of an email notification can use a named template from an external file. Create /etc/alertmanager/templates/email.tmpl with the following content: {{ define &quot;email.myorg.html&quot; }} &lt;! DOCTYPE html &gt; &lt; html &gt; &lt; body &gt; &lt; h1 &gt;{{ .Status | toUpper }}&lt;/ h1 &gt; &lt; table &gt; &lt; thead &gt; &lt; tr &gt; &lt; th &gt;Alert&lt;/ th &gt; &lt; th &gt;Summary&lt;/ th &gt; &lt;/ tr &gt; &lt;/ thead &gt; &lt; tbody &gt; {{ range .Alerts }} &lt; tr &gt; &lt; td &gt;{{ index .Labels &quot;alertname&quot; }}&lt;/ td &gt; &lt; td &gt;{{ index .Annotations &quot;summary&quot; }}&lt;/ td &gt; &lt;/ tr &gt; {{ end }} &lt;/ tbody &gt; &lt;/ table &gt; &lt;/ body &gt; &lt;/ html &gt; {{ end }} Load the template file and reference its name from the email receiver&#x27;s html field: global : smtp_smarthost : &#x27;smtp.example.org:587&#x27; smtp_from : &#x27; [email&#160;protected] &#x27; route : receiver : &#x27;email-notifications&#x27; receivers : - name : &#x27;email-notifications&#x27; email_configs : - to : &#x27; [email&#160;protected] &#x27; html : &#x27;{{ template &quot;email.myorg.html&quot; . }}&#x27; templates : - &#x27;/etc/alertmanager/templates/*.tmpl&#x27; See the &lt;email_config&gt; reference for SMTP authentication and TLS options. Sending notifications to Gotify with a custom webhook payload Gotify doesn&#x27;t have a dedicated Alertmanager receiver, but its push message API is a simple JSON POST, so it can be driven directly with the generic webhook_config and its payload field. receivers : - name : gotify webhook_configs : - url : &#x27;https://gotify.example.com/message&#x27; http_config : authorization : credentials_file : /etc/alertmanager/secrets/gotify-secret/token payload : title : &#x27;{{ .Status | toUpper }} {{ .CommonLabels.alertname }}&#x27; priority : &#x27;{{ if eq .Status &quot;firing&quot; }}5{{ else }}0{{ end }}&#x27; message : | {{ range .Alerts }}{{ .Annotations.summary }} {{ end }} A more complete version of this example, with Markdown formatting and separate sections for firing and resolved alerts, is available in examples/webhook/gotify.yml . Management API | Prometheus Prometheus Docs Download Community Support &amp; Training Blog Ctrl + K Show nav Management API Alertmanager provides a set of management API to ease automation and integrations. Health check GET /-/healthy HEAD /-/healthy This endpoint always returns 200 and should be used to check Alertmanager health. Readiness check GET /-/ready HEAD /-/ready This endpoint returns 200 when Alertmanager is ready to serve traffic (i.e. respond to queries). Reload POST /-/reload This endpoint triggers a reload of the Alertmanager configuration file. An alternative way to trigger a configuration reload is by sending a SIGHUP to the Alertmanager process.

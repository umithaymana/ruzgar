Ceph checks every object in a PG for its health. There are two forms of Scrubbing, daily cheap metadata checks and weekly deep data checks. The weekly deep scrub reads the objects and uses checksums to ensure data integrity. If a running scrub interferes with business (performance) needs, you can adjust the time when scrubs [Ceph scrubbing https://docs.ceph.com/en/tentacle/rados/configuration/osd-config-ref/#scrubbing ] are executed. 8.14.4. Mute a Health Check Muting a health check keeps it visible but excludes it from the overall health status, making new problems easier to notice. Ceph continues evaluating the check. Use a duration so that a deferred warning returns automatically, for example after two weeks: ceph health mute &lt; CHECK &gt; 2w In the web interface, expand the check under Datacenter &#8594; Ceph , click Mute , and set a duration. The check stays in the list, marked as muted; use Unmute in the same place to restore it earlier. By default, a mute clears when more items become affected. Enable Keep Mute , or add --sticky to the command, only if the check should stay muted in that case. This does not change the duration: a timed sticky mute still expires. Muting does not resolve the condition. You accept its risk for as long as the mute lasts. 8.14.5. Migrate Cephx Keys from aes to aes256k This section explains how to migrate the cluster-owned keys and the keys of compatible Ceph users from aes to aes256k . For an explanation of Ceph users, tickets, and key storage, see Cephx Authentication . Why the Health Checks Appear Ceph Squid 19.2.6 and Ceph Tentacle 20.2.4 add health checks for keys and temporary access credentials that use the older aes encryption method. The checks can therefore appear directly after an upgrade even if the cluster worked without warnings before. The older method is affected by CVE-2025-30156 . See the upstream release announcement for background [Ceph: Squid v19.2.6 and Tentacle v20.2.4 released https://ceph.io/en/news/blog/2026/v20-2-4-v19-2-6-combo-released/ ] . Two checks set the cluster status to HEALTH_ERR . This does not mean that storage access or a Ceph service has failed. Follow the steps below to migrate to aes256k and, when all clients support it, disable the vulnerable method. Migration Steps The migration helper checks the cluster, rotates keys, and resumes interrupted work. Review each dry run before applying its plan; add --verbose for full node, keyring, and device inventories and inspection diagnostics. Reruns do not rotate completed keys again. After each run, invoke the helper without options to check the current state and follow the next steps it prints. Before You Begin Upgrade pve-manager to 9.2.19 or newer and install the latest Ceph packages on every node. Staged client-key rotation requires Ceph 19.2.6-pve3, 20.2.4-pve3, or newer on every monitor. Then complete the rolling restart of all Ceph services. Resolve health warnings and errors not listed in Health Check Reference . Ensure every node is reachable over SSH. Run the helper as root on one node only. Do not start another migration, a rolling restart, or change Ceph keys with other tools while it runs. The helper&#8217;s lock does not block direct Ceph authentication commands. If Cephx is disabled on this cluster, follow Clusters with Cephx Disabled instead. 1. Migrate the Cluster-Owned Keys Review the cluster-owned migration in the default dry-run mode: /usr/share/pve-manager/migrations/pve-cephx-rotate-service-keys --rotate-cluster-keys If the plan reports no blocker, apply the same selection: /usr/share/pve-manager/migrations/pve-cephx-rotate-service-keys --rotate-cluster-keys --apply The helper rotates the manager, metadata server, OSD, monitor, bootstrap, crash, and encrypted OSD lockbox keys . It restarts services one at a time when needed, including monitors. Storage-user keys and client.admin stay unchanged, existing tickets remain valid, and the old cipher stays enabled. After Ceph updates its health status, the two error-severity checks clear. The warning about rotating service keys can remain for a few hours while old rotating keys expire. You do not need to wait for this warning to clear before continuing with the migration. 2. Migrate the Keys of Compatible Ceph Users Check compatibility Several workloads can share one Ceph user. Migrate its key only when every client supports aes256k , including disconnected and external clients. Ceph programs from the updated Proxmox VE packages support it; kernel clients require a running kernel version 7.0 or newer. Virtual machine with RBD disks Userspace, unless krbd is enabled. Container on RBD Always the kernel client. CephFS mount Kernel, unless fuse is enabled. Check external systems too. If any affected client is incompatible or unknown, leave its user&#8217;s key unchanged and postpone this step. Stage the keys Use --rotate-all-storage-keys for the dedicated users of managed local RBD and CephFS storages, together with --rotate-admin-key for client.admin , which the command line and storages without their own user share. Every client of these users is affected; storages of external clusters are excluded. The helper stages each new key and writes it to the managed keyring and secret files. Both keys remain valid until confirmation, allowing clients to refresh before the old key is retired. If a monitor cannot keep both keys valid, the helper refuses staging and names the monitor to update or restart. Review the combined plan: /usr/share/pve-manager/migrations/pve-cephx-rotate-service-keys \ --rotate-all-storage-keys --rotate-admin-key If the plan reports no blocker, apply it: /usr/share/pve-manager/migrations/pve-cephx-rotate-service-keys \ --rotate-all-storage-keys --rotate-admin-key --apply While a key is staged, do not add or downgrade monitors or change that user&#8217;s keys with other tools. Its AUTH_INSECURE_CLIENT_KEY_TYPE warning remains until confirmation makes the new key current and invalidates the old one. Refresh Clients Live-migrate affected virtual machines in the web interface, or stop and start them. A guest reboot is not enough. Stop and start affected containers and other RBD clients. Let backups, restores, disk imports, and clones on Ceph storage finish before confirmation; these operations can retain the key they started with. The helper refreshes idle CephFS mounts and leaves busy or unresponsive mounts alone. Once nothing uses them, rerun the helper with --apply to retry the outstanding mounts. If your virtual machines have ISOs from a CephFS mount attached, you may have to detach the ISOs or migrate affected virtual machines to a different node to be able to refresh the CephFS mount on that node. For clients outside Proxmox VE, distribute the staged credential from the managed key files , then restart or remount those clients. The helper reports sessions that may still hold an old key. Client hints are host-wide, not session attribution or a complete workload inventory. Sockets without an owning process are listed separately. Check disconnected clients and external key copies yourself. 3. Finish or Pause the Migration Run a final dry run to check for remaining old-key sessions. It offers a confirmation command when its observed checks pass, but cannot verify disconnected clients or external key copies for you. /usr/share/pve-manager/migrations/pve-cephx-rotate-service-keys Clients that still need an old key or cipher cannot authenticate after this step. Existing IO can appear to work until a reconnect and then fail. Do not use --force to bypass a blocker. After checking disconnected clients and external copies, run the exact command the dry run prints. When every rotation is ready and no key needs the old cipher, it will print the options --apply --confirm-all-clients-refreshed --restrict-ciphers . If any client remains incompatible, keep its key unchanged and the old cipher enabled rather than restricting it. You can mute the remaining warnings while waiting for those clients to upgrade. Use pveceph auth status for current and pending key ciphers, as ceph auth ls does not list pending keys. /etc/pve/priv/cephx-key-migration.json records progress and contains secret old keys. Protect it and keep it until the migration is complete and every client has been refreshed. Deleting it earlier loses the records needed to resume. Additional Migration Details Health Check Reference Health check Meaning Action AUTH_INSECURE_SERVICE_KEY_TYPE A Ceph service key uses the old cipher. Run the cluster-owned migration. This check has error severity. AUTH_INSECURE_SERVICE_TICKETS Monitors issue service tickets with the old cipher. Run the cluster-owned migration. This check has error severity. AUTH_INSECURE_CLIENT_KEY_TYPE The active key of a Ceph user uses the old cipher. A staged user stays listed until its rotation is confirmed. Rotate the keys of compatible users and confirm them, or mute the warning. AUTH_INSECURE_ROTATING_SERVICE_KEY_TYPE A rotating service key uses the old cipher. Continue the migration; old rotating keys expire automatically and do not prevent final cipher restriction. AUTH_INSECURE_KEYS_ALLOWED Monitors accept the old cipher. Finish the migration, or mute the warning while old clients remain. AUTH_INSECURE_KEYS_CREATABLE Monitors can create old-cipher keys. Finish the migration, or mute the warning while old clients remain.

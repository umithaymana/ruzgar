Additional Migration Details Health Check Reference Health check Meaning Action AUTH_INSECURE_SERVICE_KEY_TYPE A Ceph service key uses the old cipher. Run the cluster-owned migration. This check has error severity. AUTH_INSECURE_SERVICE_TICKETS Monitors issue service tickets with the old cipher. Run the cluster-owned migration. This check has error severity. AUTH_INSECURE_CLIENT_KEY_TYPE The active key of a Ceph user uses the old cipher. A staged user stays listed until its rotation is confirmed. Clusters with Cephx Disabled Ceph evaluates these health checks from the stored keys and cipher settings, also when Cephx is disabled, that is, when auth_cluster_required , auth_service_required , and auth_client_required are set to none . Disabling Cephx therefore does not clear them, and changing the authentication method interrupts existing clients, which need a restart or remount afterwards. On a cluster with Cephx disabled: Run the helper without options and apply its plan. It migrates the manager, metadata server, and OSD keys, restarting services one at a time when needed, and switches the service tickets to the new cipher. This clears both error-severity checks. If an old mon. key is stored in the authentication database, the helper instead refuses and asks you to migrate that key first. Optionally, migrate the bootstrap and crash keys with --rotate-client-keys . Mute the remaining warnings without a duration. While Cephx is disabled, the helper does not migrate the keys of other Ceph users, as their clients do not authenticate with Cephx: ceph health mute AUTH_INSECURE_CLIENT_KEY_TYPE --sticky ceph health mute AUTH_INSECURE_KEYS_ALLOWED --sticky ceph health mute AUTH_INSECURE_KEYS_CREATABLE --sticky Do not restrict the allowed ciphers or forbid creating old-cipher keys by hand while the preferred cipher is still aes , as creating keys then fails. Before you enable Cephx again, unmute these checks and make sure that every monitor, Ceph service, and client still has a key file matching the authentication database. Restart the monitors first, then all other Ceph services, and restart or remount the clients. Then run the migration as described in Migration Steps . Staged Keys and Confirmation The helper disables automatic promotion of pending client keys so that the monitors keep both credentials valid. An older monitor would promote a staged key on its first use and end the grace period for the whole cluster. The helper therefore stages only when every monitor supports the feature and checks this again on every run. With --apply , --confirm-all-clients-refreshed makes every staged key current and invalidates its previous key. The initial check refuses the entire batch if any open rotation is not ready. The helper then rechecks each key before retiring its old credential. If a client returns during the batch, completed rotations stay committed and the blocked key stays staged. To confirm ready users separately, use --confirm-clients-refreshed &lt;USER&gt; with --apply . Ceph 19.2.6-pve4 and 20.2.4-pve4 or newer monitors can identify each session&#8217;s key, allowing refreshed clients to stay connected during forward or rollback confirmation. Upgrade and restart older monitors to use this feature. Without key identification, every visible client of that user must disconnect before confirmation; upgrading is preferable for a shared user such as client.admin . Key Copies for External Clients For an external client of the local cluster, copy the staged credential from the managed file for its Ceph user: RBD keyring: /etc/pve/priv/ceph/&lt;STORAGE_ID&gt;.keyring CephFS bare secret: /etc/pve/priv/ceph/&lt;STORAGE_ID&gt;.secret Administrative keyring: /etc/pve/priv/ceph.client.admin.keyring Use the credential for that user, not client.admin as a substitute. Transfer it securely and update every saved copy before refreshing the client. Storage backed by an external cluster is different: the helper never rotates that cluster&#8217;s keys. Follow its administrator&#8217;s key-rotation procedure. A storage with monhost set counts as external even if its monitors belong to the local cluster, so the helper does not update its key copy. If that copy holds the key of a Ceph user you migrate, update it with the staged key of the same user before confirming, or with the restored key before confirming a rollback. The helper refuses to retire a key it finds in a storage key copy; verify copies it cannot check yourself. The helper lists local users not managed by Proxmox VE separately. Follow their client&#8217;s supported rotation procedure, or leave their keys unchanged and keep the old cipher enabled. Roll Back a Staged Client Key To return a staged user to its current key: Run the helper with --abort-staged-key &lt;USER&gt; --apply . It restores the current key to every managed copy while both credentials remain valid. Refresh all clients back to that key, including disconnected clients and external key copies. The helper retries managed CephFS mounts as during forward migration. Run the helper with --confirm-abort-clients-refreshed &lt;USER&gt; --apply to retire the staged key. The helper refuses if monitor session collection is incomplete, a visible session uses the staged key, its key is unknown, or a storage key copy still holds the staged key. Emergency Cipher Override Monitors normally use the auth_allowed_ciphers list stored in the MonMap to decide which key ciphers may authenticate. The local startup option mon_auth_emergency_allowed_ciphers replaces that list for a monitor. It can temporarily allow the cipher of an existing administrative key after an incorrect restriction locked administrators out [Ceph: Emergency Allowed Ciphers https://docs.ceph.com/en/tentacle/rados/configuration/auth-config-ref/#emergency-allowed-ciphers ] . Ceph raises AUTH_EMERGENCY_CIPHERS_SET while this override is configured. The helper refuses the final restriction because changing the MonMap would not take effect. Use the override only to recover access, then repair the normal configuration, remove it from /etc/pve/ceph.conf , and restart every monitor before the final dry run. Interrupted Runs and Manual Fallback After an interruption, run the helper without options once the affected nodes are reachable. Unfinished key updates can resume while their daemons are stopped. Keep the journal unchanged and follow the printed next steps rather than starting a manual rotation. Check the affected nodes and service logs rather than assuming a down daemon&#8217;s key needs repair. If the helper still cannot proceed, install the latest pve-manager and retry.

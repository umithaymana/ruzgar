--- layout: default title: Restoring ISM from a snapshot parent: Index State Management nav_order: 25 --- # Restoring ISM from a snapshot **Introduced 3.10** {: .label .label-purple } Index State Management (ISM) stores policies and the policy progress of each [managed index]({{site.url}}{{site.baseurl}}/im-plugin/ism/managedindexes/) in the `.opendistro-ism-config` system index. If you restore `.opendistro-ism-config` from a snapshot, such as when migrating to another cluster, each managed index resumes its policy from the state recorded in the snapshot. For managed indexes to resume their policies, you must restore them before you restore `.opendistro-ism-config`. ## Restoration order ISM can match an index to its saved progress only if the index already exists when `.opendistro-ism-config` is restored. ISM matches saved progress to an index using the index name and creation date. If an index was deleted and then recreated under the same name, it has a new creation date. ISM doesn't match the recreated index to its saved progress, so the index starts its policy from the beginning. Using the [Restore Snapshot API]({{site.url}}{{site.baseurl}}/api-reference/snapshots/restore-snapshot/), restore indexes in the following order: 1. Restore the managed indexes and wait for the restore operation to finish: ```json POST /_snapshot/my-repository/snapshot-1/_restore?wait_for_completion=true { "indices": "my-index-*", "include_global_state": false } ``` {% include copy-curl.html %} 1. Restore `.opendistro-ism-config` in a separate request: ```json POST /_snapshot/my-repository/snapshot-1/_restore { "indices": ".opendistro-ism-config", "include_global_state": false } ``` {% include copy-curl.html %} If you restore `.opendistro-ism-config` first or in the same request as the managed indexes, ISM can't match the managed indexes to their saved progress. Indexes that were attached to a policy by an ISM template restart the policy from the beginning. ISM stops managing indexes that were attached using the [Add Policy API]({{site.url}}{{site.baseurl}}/im-plugin/ism/api/#add-policy). ## Permissions If the Security plugin protects system indexes in your cluster, restoring `.opendistro-ism-config` requires permission to restore system indexes. A user mapped to a role in `plugins.security.restapi.roles_enabled` can restore a system index if the index is listed in the `plugins.security.system_indices.restore.indices` setting. `.opendistro-ism-config` is listed by default. For other ways to get write access to a protected system index, see [Write protection]({{site.url}}{{site.baseurl}}/security/configuration/system-indices/#write-protection).

--- layout: default title: Settings parent: Index State Management nav_order: 50 --- # ISM settings We don't recommend changing these settings; the defaults should work well for most use cases. Index State Management (ISM) stores its configuration in the `.opendistro-ism-config` index. Don't modify this index without using the [ISM API operations]({{site.url}}{{site.baseurl}}/im-plugin/ism/api/). All settings are available using the OpenSearch `_cluster/settings` operation. None require a restart, and all can be marked `persistent` or `transient`. To learn more about static and dynamic settings, see [Configuring OpenSearch]({{site.url}}{{site.baseurl}}/install-and-configure/configuring-opensearch/index/). Because ISM settings are cluster settings, persistent ISM settings are part of the global cluster state and are included in a snapshot taken with `include_global_state` set to `true`. Transient settings are not included. ISM policies are stored in the `.opendistro-ism-config` index, not in the cluster state, so a snapshot includes them only if it includes that index. For more information, see [Global cluster state]({{site.url}}{{site.baseurl}}/tuning-your-cluster/availability-and-recovery/snapshots/snapshot-restore/#global-cluster-state). These settings apply only to ISM jobs. The Job Scheduler plugin, which runs ISM jobs, has separate settings that apply to the scheduled jobs of all plugins. For more information, see [Scheduled job settings]({{site.url}}{{site.baseurl}}/tuning-your-cluster/scheduled-jobs/index/#scheduled-job-settings). Setting | Default | Description :--- | :--- | :--- `plugins.index_state_management.enabled` | True | Specifies whether ISM is enabled or not. `plugins.index_state_management.job_interval` | 5 | The interval (in minutes) at which the managed index jobs are run. `plugins.index_state_management.jitter` | 0.6 | A randomized delay that is added to a job's base run time to prevent a surge of activity from all indexes at the same time. A value of 0.6 means a delay of 0--60% of a job interval is added to the base interval. For example, if you have a base interval time of 30 minutes, a value of 0.6 means an amount anywhere between 0 to 18 minutes gets added to your job interval. Maximum is 1, which means an additional interval time of 100%. This maximum cannot exceed `plugins.jobscheduler.jitter_limit`, which also has a default of 0.6. For example, if `plugins.index_state_management.jitter` is set to 0.8, ISM uses `plugins.jobscheduler.jitter_limit` of 0.6 instead. `plugins.index_state_management.coordinator.sweep_period` | 10m | How often the routine background sweep is run. `plugins.index_state_management.coordinator.backoff_millis` | 50ms | The backoff time between retries for failures in the `ManagedIndexCoordinator` (such as when we update managed indexes). `plugins.index_state_management.coordinator.backoff_count` | 2 | The count of retries for failures in the `ManagedIndexCoordinator`. `plugins.index_state_management.history.enabled` | True | Specifies whether audit history is enabled or not. The logs from ISM are automatically indexed to a logs document. `plugins.index_state_management.history.max_docs` | 2500000 | The maximum number of documents before rolling over the audit history index. `plugins.index_state_management.history.max_age` | 24h | The maximum age before rolling over the audit history index. `plugins.index_state_management.history.rollover_check_period` | 8h | The time between rollover checks for the audit history index. `plugins.index_state_management.history.rollover_retention_period` | 30d | How long audit history indexes are kept. `plugins.index_state_management.allow_list` | `alias`, `allocation`, `close`, `convert_index_to_remote`, `delete`, `force_merge`, `index_priority`, `notification`, `open`, `read_only`, `read_write`, `replica_count`, `rollover`, `rollup`, `search_only`, `shrink`, `snapshot`, `stop_replication`, `transform` | The actions that a policy can use. Removing an action from this list makes every policy that uses it fail. `plugins.index_state_management.action_validation.enabled` | False | Specifies whether ISM validates an action before running it.

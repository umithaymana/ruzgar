For example, if `source_prefix` is `listed/` and the index has two shards, shard 0 reads `listed/0/` and shard 1 reads `listed/1/`. Listing includes nested folders up to 64 levels deep. A shard lists its folder each time it starts, including after a restart, a relocation, or a settings update. Place all objects in the folders before you create the index, and don't change them during ingestion. If objects change between listings, the shard processes them as follows: * An object added after the previous listing is read only if its name sorts after the object that the shard was reading. * An unread object that was removed is skipped. * A resized object is read up to its new size. * If the object that the shard was reading was removed and other objects remain in the folder, the shard pauses. * If no objects remain in the folder, the shard reads nothing and reports a lag of `0`. Objects that are not in any shard folder are not read. ## Dividing objects among shards Each shard determines its own portion of the objects from the same settings, so each record is read by exactly one shard. The `shard_split` parameter supports the following values: * `whole_files`: Each object is assigned to one shard based on a hash of its key. This method balances the number of objects per shard and does not account for object size. * `shard_prefixes`: Objects in ` /N/` are assigned to shard `N`. * `equal_bytes`: The single object specified in `source_url` is divided into one byte range per shard. Each range boundary is moved forward to the start of the next line so that no record is split between shards. The manifest must contain exactly this one object, and its size must be greater than 0. ## Exactly-once ingestion Each document ID is built from the shard number, the object key, and the byte offset at which the record starts. If a record is read again after a crash or restart, it receives the same ID and overwrites the earlier copy, so each record produces exactly one document. ## Monitoring ingestion progress The `consumer_stats.pointer_based_lag` metric reports the number of bytes that the shard has not yet read. Ingestion is complete when this metric is `0` on every shard. For more information, see [Pull-based ingestion metrics]({{site.url}}{{site.baseurl}}/im-plugin/pull-based-ingestion/index/#pull-based-ingestion-metrics). ## Errors The following errors pause the shard: * A configuration error. The reason is written to the logs. * A read error, such as a missing object or a reached cost limit. * An object size mismatch. The source verifies that each object has its declared size. If an object is shorter or longer than declared, or is declared empty but contains data, the shard pauses so that partial data is not indexed. Lines that cannot be parsed are handled according to the `error_strategy` setting. For more information, see [Updating the error policy]({{site.url}}{{site.baseurl}}/im-plugin/pull-based-ingestion/index/#updating-the-error-policy). ## Limitations The object store source has the following limitations: * Compressed files, such as gzip files, are not supported. * You cannot change the `manifest`, `source_url`, `source_prefix`, `shard_split`, or `discovery` parameters on an existing index. To change these parameters, create a new index. ## Related documentation * [Pull-based ingestion]({{site.url}}{{site.baseurl}}/im-plugin/pull-based-ingestion/index/) * [Pull-based ingestion management APIs]({{site.url}}{{site.baseurl}}/api-reference/index-apis/pull-based-ingestion-management/)

--- layout: default title: Refresh search analyzer parent: Tuning indexes nav_order: 10 has_toc: false redirect_from: - /query-dsl/analyzers/refresh-analyzer/ - /im-plugin/refresh-analyzer/index/ --- # Refresh search analyzer Use the Refresh Search Analyzer API to apply a change to a search analyzer's resource files in real time. For example, if you change the synonym list in your analyzer, the change takes effect without you needing to close and reopen the index: ```json POST /_plugins/_refresh_search_analyzers/{index} ``` {% include copy-curl.html %} ## Path parameters The following table lists the available path parameters. All path parameters are required. | Parameter | Data type | Description | | :--- | :--- | :--- | | `index` | String | A comma-separated list of indexes, data streams, or index aliases to which the operation is applied. Supports wildcard expressions (`*`). Use `_all` or `*` to specify all indexes and data streams in a cluster. | ## Query parameters The following table lists the supported query parameters. Parameter | Data type | Description :--- | :--- | :--- `reload_cached_resources` | Boolean | When set to `true`, reloads cached resources from disk without rebuilding caches for token filters that load files from disk (for example, the [`hunspell`]({{site.url}}{{site.baseurl}}/analyzers/token-filters/hunspell/) filter's dictionary files). When `false` (the default), analyzer factories are rebuilt but cached resources are reused. ## Making a token filter updatable A token filter is only refreshed if it has an `updateable` flag of `true`. An updatable filter can be used only in a search analyzer, not in an index analyzer, because existing documents are not reanalyzed. The following request creates an index with an updatable synonym filter and applies it as the search analyzer for the `desc` field: ```json PUT /synonym_index { "settings": { "index": { "analysis": { "analyzer": { "my_synonyms": { "tokenizer": "whitespace", "filter": [ "synonym" ] } }, "filter": { "synonym": { "type": "synonym_graph", "synonyms_path": "analysis/synonyms.txt", "updateable": true } } } } }, "mappings": { "properties": { "desc": { "type": "text", "analyzer": "standard", "search_analyzer": "my_synonyms" } } } } ``` {% include copy-curl.html %} The `synonyms_path` is relative to the `config` directory of each node. After you edit the file, refresh the analyzer: ```json POST /_plugins/_refresh_search_analyzers/synonym_index ``` {% include copy-curl.html %} ## Example response The response lists the analyzers that were refreshed in each index: ```json { "_shards": { "total": 1, "successful": 1, "failed": 0 }, "successful_refresh_details": [ { "index": "synonym_index", "refreshed_analyzers": [ "my_synonyms" ] } ] } ``` Searches against `desc` now use the updated synonym list.

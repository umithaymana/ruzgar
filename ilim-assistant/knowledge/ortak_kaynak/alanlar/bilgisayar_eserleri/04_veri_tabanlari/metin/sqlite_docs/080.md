Most dot-commands can be abbreviated. For example ".q" is a common abbreviation for ".quit". 3. Rules for dot-commands, SQL, and More 3.1. Line Structure The CLI's input is a mixed sequence of: SQL statements dot-commands CLI comments SQL statements are free-form, and can be spread across multiple lines, with whitespace or SQL comments embedded anywhere. Multiple SQL statement are accumulated until a line is seen that ends with ";" when ignoring trailing whitespace and that contains one or more complete SQL statements. Note that ";" can occur internally in a CREATE TRIGGER statement. SQLite knows this and will not try to evaluate the SQL until the CREATE TRIGGER statement is complete. When such a trailing ";" is seen, all accumulated SQL statements are evaluated together. Dot-command have a specific syntax: Dot-commands must begin with a "." at the left margin with no preceding whitespace. Dot-commands must be entirely contained on a single input line. Dot-commands cannot occur in the middle of an ordinary SQL statement. In other words, dot-commands cannot occur at a continuation prompt. There is no comment syntax for dot-commands. Bare (unquoted) semicolons at the end of dot commands are ignored (in version 3.52.0 and after). The CLI also accepts whole-line comments that begin with a '#' character and extend to the end of the line. There can be no whitespace prior to the initial '#'. 3.2. Dot-command arguments Dot-commands can be followed by zero or more space-separated arguments. Arguments are parsed according to these rules: Any trailing whitespace and a final ";" are removed, if present. Arguments are separated from each other and from the initial dot-command itself by whitespace. Text within '...' is treated as a single argument with the ' delimiters removed, even if the text contains white space. Text within "..." is treated as a single argument with the " delimiters removed. C-style backslash escapes (ex: \\ , \n , \r , \" , \033 , etc.) work only within double-quoted arguments. 3.3. Dot-commands are evaluated separately The dot-commands are interpreted by the sqlite3.exe command-line program, not by the SQLite library. So dot-commands will not work as an argument to core SQLite library interfaces such as sqlite3_prepare() or sqlite3_exec() . 4. Output Formats The CLI can show SQL query results in a rich variety of formats. The .mode command is used to control the formatting of query results. The details on how the .mode command works are extensive and are hence covered in a separate document . Without going into too much detail, here are a few quick examples to show how the .mode command works: .mode box &emsp; Show query results in a grid formed using Unicode box drawing characters. .mode quote Show query results as lines of comma-separated SQL literals, one line per row of output. .mode csv Show query results as CSV ("Comma-Separated Values"). .mode --list Show a list of available output modes .mode Show the current output mode .mode --once box Show the next SQL statement using "box" mode but then automatically revert back to the current mode. 5. Querying the database schema The sqlite3 program provides several convenience commands that are useful for looking at the schema of the database. There is nothing that these commands do that cannot be done by some other means. These commands are provided purely as a shortcut. For example, to see a list of the tables in the database, you can enter ".tables". SQLite-3.54 ex1.db -&gt; .tables tbl1 tbl2 SQLite-3.54 ex1.db -&gt; The ".tables" command is similar to setting list mode then executing the following query: SELECT name FROM sqlite_schema WHERE type IN ('table','view') AND name NOT LIKE 'sqlite_%' ORDER BY 1; But the ".tables" command does more. It queries the sqlite_schema table for all attached databases, not just the primary database. And it arranges its output into neat columns. The ".indexes" command works in a similar way to list all of the indexes. If the ".indexes" command is given an argument which is the name of a table, then it shows just indexes on that table. The ".schema" command shows the complete schema for the database, or for a single table if an optional tablename argument is provided: SQLite-3.54 ex1.db -&gt; .schema create table tbl1(one varchar(10), two smallint) CREATE TABLE tbl2 ( f1 varchar(30) primary key, f2 text, f3 real ); SQLite-3.54 ex1.db -&gt; .schema tbl2 CREATE TABLE tbl2 ( f1 varchar(30) primary key, f2 text, f3 real ); SQLite-3.54 ex1.db -&gt; The ".schema" command is roughly the same as setting list mode, then entering the following query: SELECT sql FROM sqlite_schema ORDER BY tbl_name, type DESC, name; As with ".tables", the ".schema" command shows the schema for all attached databases. If you only want to see the schema for a single database (perhaps "main") then you can add an argument to ".schema" to restrict its output: SQLite-3.54 ex1.db -&gt; .schema main.* The ".schema" command can be augmented with the "--indent" option, in which case it tries to reformat the various CREATE statements of the schema so that they are more easily readable by humans. The ".databases" command shows a list of all databases open in the current connection. There will always be at least 2. The first one is "main", the original database opened. The second is "temp", the database used for temporary tables. There may be additional databases listed for databases attached using the ATTACH statement. The first output column is the name the database is attached with, and the second result column is the filename of the external file. There may be a third result column which will be either "'r/o'" or "'r/w'" depending on whether the database file is read-only or read-write. And there might be a fourth result column showing the result of sqlite3_txn_state() for that database file. SQLite-3.54 ex1.db -&gt; .databases The ".fullschema" dot-command works like the ".schema" command in that it displays the entire database schema. But ".fullschema" also includes dumps of the statistics tables "sqlite_stat1", "sqlite_stat3", and "sqlite_stat4", if they exist. The ".fullschema" command normally provides all of the information needed to exactly recreate a query plan for a specific query. When reporting suspected problems with the SQLite query planner to the SQLite development team, developers are requested to provide the complete ".fullschema" output as part of the trouble report. Note that the sqlite_stat3 and sqlite_stat4 tables contain samples of index entries and so might contain sensitive data, so do not send the ".fullschema" output of a proprietary database over a public channel. 6. Opening Database Files The ".open" command opens a new database connection, after first closing the previously opened database. In its simplest form, the ".open" command merely invokes sqlite3_open() on the file named as its argument. Use the name ":memory:" to open a new in-memory database that disappears when the CLI exits or when the ".open" command is run again. Or use no name to open a private, temporary on-disk database which will also disappear upon exit or use of ".open". If the --new option is included with ".open", then the database is reset prior to being opened. Any prior data is destroyed. This is a destructive overwrite of prior data and no confirmation is requested, so use this option carefully. If the --ifexists option is included, the ".open" command only works if the database file already exists. In other words, --ifexists prevents a new, empty database from being created.
